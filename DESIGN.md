## 1. Overview & scope

`ethernet-ip-adapter` is the **Rust reference southbound protocol adapter** for
**EtherNet/IP** — the CIP (Common Industrial Protocol) encapsulation over TCP/IP used by
Allen-Bradley ControlLogix / CompactLogix PLCs and many generic CIP devices. It is the third
reference adapter (after OPC UA / Java and Modbus / Python) and the first in Rust, proving the
southbound contract is language-complete and exercising **two** corners of the design space at
once: the **tag-addressed, poll-based** model (explicit messaging, like Modbus) and the
**device-push** model (class-1 implicit I/O — cyclic produced/consumed assemblies at an RPI,
the industrial-Ethernet analog of OPC UA's subscribe side). It rides the **owned protocol stack**
(`crates/enip`, [`PROTOCOL-DESIGN.md`](PROTOCOL-DESIGN.md)) rather than an external protocol
library.

### 1.1 EtherNet/IP + CIP background (what an implementer must know)

- **EtherNet/IP** encapsulates CIP over TCP port **44818** (explicit messaging) and UDP 2222
  (implicit class-1 I/O). A TCP session is opened with an EtherNet/IP *RegisterSession*, then CIP
  requests ride *SendRRData* (unconnected) or *SendUnitData* (connected, after a CIP
  *ForwardOpen*).
- **Explicit messaging** is request/response: the client sends a CIP service (Read Tag `0x4C`,
  Write Tag `0x4D`, Get Instance Attribute List `0x55` for tag discovery) addressed by an
  **EPath**. This is the adapter's **poll** mode — scheduled polling, like the Modbus reference.
- **Implicit I/O** (class-1 cyclic UDP produced/consumed assemblies) is the device-push model:
  the adapter (as scanner/originator) ForwardOpens an I/O connection against the device's
  assembly instances; the device then produces its input assembly cyclically at the negotiated
  RPI over UDP :2222, and the adapter produces an output assembly (or heartbeat) back. This is
  the adapter's **push** mode. Assemblies are raw bytes; config maps byte offsets to typed,
  named signals (§4.6). Mode is selected **per instance** (`mode: poll | push`, D-EIP-2).
- **The AB tag model**: Logix controllers expose *tags* — named, typed variables
  (`LINE_SPEED : REAL`, `ZONE_TEMPS : REAL[8]`, program-scoped
  `Program:MainProgram.FillTimer.ACC`). A tag is addressed by its symbolic path (the EPath). CIP
  elementary types carry explicit type codes (DINT `0xC4`, REAL `0xCA`, …). Reads/writes to a
  ControlLogix CPU in a chassis are routed through a **connection path** (backplane port 1 +
  CPU slot, e.g. slot 0); devices without a backplane (CompactLogix directly, our simulator) use
  an empty/default path.
- In EdgeCommons vocabulary a data point is a **signal** (never "tag" — that word is reserved for
  envelope business metadata). A CIP tag maps to a signal: `signal.id` is its stable tag path,
  `signal.address` the protocol-native object (§5).

### 1.2 Where it sits in the site topology

One component instance (`component.instances[]` entry) = **one device** (one PLC / one CIP
endpoint), each with its own task, session, and connection lifecycle — the template's
one-task-per-instance supervisor, kept as-is. The adapter publishes `SouthboundSignalUpdate` on
the device-local bus (`data` class); `uns-bridge` uplinks to the site broker; `edge-console`
consumes the site UNS and drives the adapter through its `cmd` inbox (panels in §7.6). In the
Dallas bottling harness it joins `bottling-company-test/` as a southbound source alongside the
Modbus and OPC UA adapters, fed by the cpppo (poll) and OpENer (push) simulators (§11).

### 1.3 In scope / out of scope

**In scope (v1):** the **owned protocol stack** (`crates/enip`, its own design doc); **poll
mode** — scheduled polling of config-declared signals (scalars + arrays) over CIP explicit
messaging (unconnected and connected class-3); **push mode** — class-1 implicit I/O
(produced/consumed assemblies at an RPI, P2P and multicast consume, run/idle, sequence/stale/
timeout validation) with config-declared assembly layouts; confirmed allow-listed writes in both
modes; the full `sb/*` command family incl. the **`sb/pause` / `sb/resume` contract extension**
(per-instance, both modes); CIP tag discovery (`sb/browse`) where the device supports it; full
metric-family parity with Modbus/OPC UA plus a push-mode I/O family; per-instance connectivity +
paused reflection; deadband/on-change publishing with batching; decoder **fuzzing**; Diátaxis
docs; 90% coverage gate (workspace-wide); all three platform packs.

**Out of scope (v1, stated in §14):** UDT/structure values; Logix STRING (a UDT); CIP Multiple
Service Packet request batching; **DTLS on the implicit (class-1) path** and CIP Security
device-side commissioning (writing a target's security objects). CIP Security Phase 2 is shipped on
the *explicit* path: TLS (Phase 1, `connection.security` + D-EIP-21, §14.5), target posture reads
(Phase 2a, D-EIP-22), vault-native trust/cert lifecycle (Phase 2b, D-EIP-23), and **originator-side
EST enrollment/renewal (Phase 2c, D-EIP-24)** — the adapter enrolls its *own* client certificate; it
is not a CIP Security *target*. Acting as a class-1 *target* in production (the test harness ships a
minimal target, PROTOCOL-DESIGN §12.5); store-and-forward
(Tier-2 core concern); editing core `SOUTHBOUND.md` (pause/resume promotion is *proposed*, not
performed, by this work).

## 2. Decisions register

| # | Decision | Rationale / alternatives |
|---|---|---|
| **D-EIP-1** | **Protocol stack = the OWNED pure-Rust `crates/enip` crate ([`PROTOCOL-DESIGN.md`](PROTOCOL-DESIGN.md)). No external protocol library.** *(Supersedes v1.0's "use rseip 0.3".)* | Both vetted OSS options failed the bar: `rseip` is frozen, panics on a truncated reply, has UTF-8 UB in tag listing, and correlates connected replies with a `debug_assert!` only (silent wrong-tag values in release builds); `EIPScanner` (C++) overruns on runt I/O frames and swallows sequence/size validation — and neither is maintained. On a wire where every inbound byte is device/attacker-controlled, we own the stack: memory-safe bounds-checked decoding (`#![forbid(unsafe_code)]`), real reply correlation with per-request deadlines, validated class-1 consumption, fuzzed decoders. Both references were studied for wire-format correctness (they agree with each other and with ODVA on every layout); the code is original. Pure Rust ⇒ builds natively on Windows/MSVC, Linux, and the Greengrass WSL path with zero C deps. The 2026-07-18 cpppo de-risk probe stands as *wire* validation (read `LINE_SPEED`, wrote+read back `FILL_SETPOINT`); its rseip API pattern is retired with this decision. |
| **D-EIP-2** | **Update model = BOTH: `mode: "poll"` (scheduled explicit-messaging polling, the default) and `mode: "push"` (class-1 implicit I/O), selected per instance.** *(Supersedes v1.0's "poll-only, implicit I/O unsupported" — that limit was rseip's, and rseip is gone.)* | Poll mirrors the Modbus poll-group model (groups + deadband + on-change publish). Push consumes the device's cyclic input assembly at the RPI and maps configured byte-offset fields to signals (§4.6); publish gating (deadband/onChange/batch/sample floor) still applies so a 10 ms RPI does not flood the UNS. One instance = one device = one mode; a plant that wants both from one PLC configures two instances. |
| **D-EIP-3** | **`sb/pause` / `sb/resume` are a deliberate southbound-contract EXTENSION.** | Neither reference adapter has them; `SOUTHBOUND.md` §2.2 does not list them. They are designed fully here (§7.4, §9) and are a **candidate for promotion into core `SOUTHBOUND.md`** as a poll-adapter convention — but this work does NOT edit core. Surfaced up front per the fidelity contract. *Resolved: `SOUTHBOUND.md` §2.2 (core 0.4.0) now ships `sb/pause`/`sb/resume`/`reconnect`/`repoll` as the standard instance-control family — see D-EIP-25.* |
| **D-EIP-4** | **Naming: repo/crate/bin `ethernet-ip-adapter`; component `com.mbreissi.edgecommons.EthernetIpAdapter`; UNS component token `ethernet-ip-adapter` (via the config `component.token` override); `device.adapter` = `"ethernet-ip"`.** | Matches the sibling kebab convention (`modbus-adapter`, `opcua-adapter`). The CLI mangled the crate name to `ethernetipadapter` with no override (CLI-DOGFOODING #1/#2); the current tree still carries that name in `Cargo.toml`/`Dockerfile`/`recipe.yaml`/`compose.yaml`/`supervisor/` — renaming them all is implementation slice S1. `component.token` is a shipped core feature (`config/identity.rs`: `configured_component_token` overrides the PascalCase short name), so the UNS token is `ethernet-ip-adapter` without renaming the Greengrass component. |
| **D-EIP-5** | **Writes are allow-listed and secure-by-default: empty `writes.allow[]` ⇒ ALL writes refused, matched on the stable `signal.id`.** | Keeps the template's gate verbatim (checked in the command handler before the write reaches the device task) and the D-U16 convention. Deliberately *not* Modbus's legacy boolean `write.enabled` — the allow-list is the target contract (`SOUTHBOUND.md` §2.2) and strictly stronger. |
| **D-EIP-6** | **Two live simulators, both EXTERNAL containers, one per mode: cpppo (AB tag server, :44818) for POLL; an OpENer target container for PUSH.** No embedded/in-crate test server anywhere (user decision). The in-process sim backend stays and is extended to model both. | Unit tests reach 90% with no PLC and no network — the protocol crate's session/connection logic is driven over in-memory `tokio::io::duplex` byte-stream fixtures (PROTOCOL-DESIGN D-ENIP-14) and the adapter backend over the sim backend / a mock `DeviceSession`; E2E and sim-gated integration tests talk to the real wire (§11). cpppo cannot serve class-1 implicit I/O, so push needs a real target: OpENer is the independent-implementation conformance peer (§11.5). Push integration gates on the external OpENer container exactly as poll gates on cpppo — there is no our-code-to-our-code CI fallback. Coverage: no product file is excluded from the 90% gate — the loop drivers take their live dependencies through injected seams (`Publisher`, `DeviceBackend`/`DeviceSession`/`PushSession`, `EventSink`) and the EtherNet/IP backend through a loopback peer, so they are unit-tested too; these live suites are the independent-implementation conformance evidence, which is a separate question from coverage (§12.2). |
| **D-EIP-7** | **Signals are declared explicitly in config poll groups; `sb/browse` is on-demand discovery, not subscription matching.** | Modbus-style declaration (no regex include/exclude like OPC UA — that model belongs to a subscription protocol). `sb/browse` uses the Logix tag-list service (Get Instance Attribute List, `EipClient::list_tags`) so a console can discover tags; generic CIP devices may not implement it ⇒ `BROWSE_UNSUPPORTED` (§7.3, §14.4). *The paging contract that discovery rides — cursor validation, truthful `max`, and the walk's termination guards — is D-EIP-29.* |
| **D-EIP-8** | **Poll mode: `connection.connected: false` is the default (unconnected explicit messaging); `true` opens a class-3 CIP connected session (ForwardOpen).** | Unconnected is the simplest path and what cpppo serves. Connected class-3 (PROTOCOL-DESIGN §7.6) allocates a connection for higher-rate polling against real PLCs — supported, config-selected, validated in the lab (not against cpppo). Push mode always uses its own class-1 ForwardOpen and ignores this key. |
| **D-EIP-9** | **`signal.id` = the configured `tagPath`, verbatim (case-sensitive).** | One instance = one device, so the tag path is unique within the instance and stable across restarts — no synthetic prefix needed (`u<unit>/…` exists in Modbus because unit id is real addressing there; slot is connection routing, not identity, so it stays out of the id and inside `signal.address`). The UNS topic channel comes from the config `name` (lower-kebab), NOT from the id — §5.3/§6.1. |
| **D-EIP-10** | **Quality: per-signal read failure ⇒ published `BAD` sample with the CIP status in `qualityRaw`; connection-level failure ⇒ leave the poll loop and reconnect; `UNCERTAIN` for scale/coercion anomalies.** | Keeps the template's "a failed read is published, not swallowed" rule and the §3 normalization table (§5.4). |
| **D-EIP-11** | **Timestamps: `serverTs` = adapter read time (facade default "now"); `sourceTs` is NEVER emitted.** | CIP explicit read replies carry no device timestamp. The facade never synthesizes `sourceTs`, honoring `SOUTHBOUND.md` §2 ("at least one SHOULD be present" — `serverTs` is). |
| **D-EIP-12** | **Metric families: mandatory `southbound_health` (exactly the eight SOUTHBOUND §5 measures, incl. `signalsSubscribed`) PLUS `EtherNetIpConnection` / `EtherNetIpInventory` / `EtherNetIpPoll` / `EtherNetIpPublish` / `EtherNetIpCommand` / `EtherNetIpIo` (push), every counter as a `(…Total, …Interval)` measure pair.** | Family structure and dimensions mirror Modbus (`Modbus*` families, dims `instance`/`pollGroup`/`result`/`verb`/`publishMode`); the explicit Total/Interval measure-pair spelling mirrors OPC UA (`ReadRequestTotal`/`ReadRequestInterval`). `EtherNetIpIo` is the push-mode addition (frames, sequence gaps, stale drops, watchdog timeouts — §8.8), surfacing the validation counters the protocol stack keeps (PROTOCOL-DESIGN §8.6). This is the parity superset — full tables in §8. Dimensions are low-cardinality ONLY; tag names/addresses/endpoints are never dimensions. |
| **D-EIP-13** | **Command routing: all verbs registered ONCE on the one inbox; the target device is the addressed instance, optional when exactly one device is configured.** | Exactly the Modbus pattern (each verb registered once, one inbox serving every device this adapter owns — D-U28). *Amended by D-EIP-26: the addressing itself (topic token, `body.instance`, conflict refusal) is library-owned; the optional-iff-one default and `NO_SUCH_INSTANCE` stay here because they need this adapter's configuration.* |
| **D-EIP-14** | **Pause semantics (poll mode): pause suspends the *scheduled poll/publish* only. The session stays open, on-demand `sb/read`/`sb/write` still work, and a slow keepalive probe keeps `connected` driven by real CIP I/O.** (Push-mode counterpart: D-EIP-20; the mode-uniform contract — pause suspends the instance's telemetry production — is normative in §7.4.) | The alternative (tear the session down) conflates "operator muted the data flow" with "link is down" and would make `connected` a lie in both directions. Full semantics in §7.4/§9.3. Pause state is **in-memory** — a component restart resumes production (documented; a persistent disable would be config, not a command). |
| **D-EIP-15** | **One CIP request per signal per poll cycle (no Multiple Service Packet batching) in v1.** | MSP batching is a performance optimization with real encoding complexity; with the owned stack it is now *feasible* (a natural `enip` crate v2 feature) but still deliberately deferred. Stated as a limitation (§14.3) with the `EtherNetIpInventory.requestsPerCycle` measure making the cost visible. Push mode does not have this cost (one frame carries the whole assembly). |
| **D-EIP-16** | **Supported value types: CIP elementary scalars + 1-D arrays thereof. `string`/UDT/structs are rejected at config validation. `bool` + `arrayCount` is ACCEPTED and labelled EXPERIMENTAL — a per-signal validation WARNING, not a refusal.** | The owned codec decodes every elementary type (§5.1 incl. usint/uint/udint/ulint/lreal); Logix STRING is a UDT and struct *values* are out of scope for v1 (the stack detects and reports them — PROTOCOL-DESIGN §6.3). Rejecting at startup with a clear error beats a runtime surprise (§5.2, §14.2). Applies to both poll `type` and push field `type`. **BOOL-array amendment (user decision):** the codec encodes a BOOL array byte-per-element (`0xC1`), and the one canonically known device behavior differs — "Logix BOOL arrays are multiples of BOOL[32] and are implemented as a DWORD array" (Rockwell 1756-PM020, p. 58), so a ControlLogix/CompactLogix answers a `BOOL[n]` read with `0x00D3` 4-byte words. **That reply is now TRANSLATED, not refused (D-EIP-35):** the packed representation is the same logical type in the device's storage, so it is unpacked LSB-first into the configured N booleans and published GOOD. What stays EXPERIMENTAL is the label on the feature, not a predicted failure: the packed path has never met a physical controller, its bit order and packed element-count denomination are read out of PM020 rather than measured, and a write to a tag observed packed is refused (it needs a masked read-modify-write). The resolution is **availability with honesty, not conditional correctness**: the signal is configurable, and every launch emits one WARN per offending signal saying which representations are read, that the packed one is unvalidated against physical hardware, and that packed writes are refused. It is stated that way because **the adapter has no device-family detection** — there is no config knob and no identity-based dispatch (`slot` is backplane routing, not device identity), and the poll path speaks the Logix data-access services (`0x4C` Read Tag by tagPath) by construction — so the adapter cannot evaluate any per-device-category claim, and the experimental label is therefore **global to the feature**. cpppo is *not* evidence that byte-per-element is right anywhere: it is a Logix emulator with a fidelity gap at exactly this point (it serves BOOL arrays byte-per-element), which is why the sim harness cannot validate this feature at all and why a green bench proves nothing here. **DWORD packing is implemented (D-EIP-35) and remains hardware-gated** — the §14.6 lab-hardware row now reads as confirmation of the bit order, the element-count denomination, and the masked write, not as the implementation itself. The alternative considered and rejected by the user was refusing `bool` + `arrayCount` outright: it removes a capability that may work on some targets in order to prevent a failure that is already loud, and a startup refusal is a worse trade than a startup warning. Reach: the warning is a *value* returned by validation (`DeviceConfig::experimental_signal_warnings`, the shape `unmatched_allow_entries` already uses) and logged by the launcher with instance context, so it is asserted by a test rather than emitted into the void; a sample that still fails carries the generalized "expected …, device declares …" detail (D-EIP-35) for the operator who never saw the startup log; and `sb/browse` reports a 1-D `BOOL` symbol `supported: true`, because the signal is configurable. Scalar `bool` and push assembly `bool` array fields are untouched — a push layout is the adapter's own declared byte map (D-EIP-18), not Logix tag storage. |
| **D-EIP-17** | **The repo is a Cargo workspace: `crates/enip` (protocol library) + `crates/ethernet-ip-adapter` (this binary). The protocol crate knows NOTHING about EdgeCommons** — no UNS, envelopes, metrics, commands, config schema, or edgecommons dependency; the adapter consumes it only through the `device.rs` seam. | The isolation is what makes the stack independently testable, fuzzable, and reusable (PROTOCOL-DESIGN §1). Mirrors the `core/cli` workspace convention. The old "thin rseip call seam excluded from coverage" carve-out dies with this: the protocol crate is inside the 90% gate. |
| **D-EIP-18** | **Push signals are config-declared assembly-layout fields** (`byte offset + type [+ bit] [+ arrayCount]` within the input/output assembly), with stable `signal.id` = `a<assemblyInstance>/<offset>/<type>[.<bit>]`. | Raw I/O is just bytes — the layout IS the signal model (the Modbus register-map analog for push). The id form mirrors Modbus's `u<unit>/<table>/<addr>/<type>`: derived from real addressing, stable across restarts, independent of the display `name`. Bounds are validated at startup by the crate's `AssemblyLayout` (construction-time, so runtime extraction cannot go out of bounds). |
| **D-EIP-19** | **Decoder fuzzing is a release gate**: the protocol crate's cargo-fuzz targets (PROTOCOL-DESIGN §12.3) run in CI on every PR (short budget, checked-in corpus + regressions); a reproducible panic/OOM found by fuzzing is a ship blocker. | The memory-safety claim (D-EIP-1's reason to exist) must be executable, not aspirational. Fuzzing runs on Linux (CI/WSL — libFuzzer). |
| **D-EIP-20** | **Pause in push mode keeps the I/O connection OPEN**: O→T production continues (heartbeat/outputs, run/idle unchanged), consumed frames still update the last-value snapshot and drive connectivity — but nothing is published to `data`. | Per-instance pause suspends *telemetry production* whichever mode the instance runs (user clarification). Closing the connection would conflate "operator muted the data flow" with "link is down" (same rationale as D-EIP-14), and stopping O→T production would make the *target* time the connection out (PROTOCOL-DESIGN D-ENIP-9). Push needs no keepalive probe: T→O reception itself is the liveness signal. |
| **D-EIP-21** | **CIP Security Phase 1 — TLS on the explicit (poll) path.** A poll instance's `connection.security` block (`mode: plaintext\|tls`, client identity, CA, `verifyPeer`, `serverName`, `checkExpiration`, `cipherSuites`) wraps the explicit-messaging session in mutual X.509 TLS on TCP 2221 via `enip::connect_tls` (crate `tls` feature). The adapter builds the `rustls::ClientConfig`; the crate stays EdgeCommons-free. Cert/key/CA material is sourced by exactly one style per credential — a vault bundle/secret (`certSecret`/`ca.secret`), files (`certFile`/`keyFile`/`ca.file`), or an inline `{"$secret": …}` content ref (`client.cert`+`key`/`ca.cert`); mixing styles is a startup error. `tls` on a push instance is refused (no DTLS, no silent downgrade). | Poll mode is the security-sensitive path (writes) and TLS-on-TCP maps 1:1 onto the transport-generic session-actor seam (PROTOCOL-DESIGN §11.1). Only AEAD suites are negotiable — the `rustls` ring provider with `tls12` on offers the three TLS 1.3 suites plus six TLS 1.2 ECDHE suites (four AES-GCM, two ChaCha20-Poly1305), and `cipherSuites` can only narrow that set — so CBC, NULL and PSK are unreachable; CBC-only legacy firmware is a documented interop boundary (typed `NoCipherOverlap`). The three sourcing styles honor the ecosystem `$secret` convention while keeping file/vault/inline unambiguous. DESIGN-cip-security.md §3. |
| **D-EIP-22** | **CIP Security Phase 2a — security-posture reads (originator).** On connect the adapter reads the target's CIP Security (0x5D), EtherNet/IP Security (0x5E), and Certificate Management (0x5F) objects and surfaces the decoded posture on `sb/status.security.target` (+ `targetSupportsCipSecurity`) and the session's `SecurityStatus`. The `enip` crate carries typed, bounds-checked (`WireReader`) decoders (`cip/security.rs`) over the shipped `get_attribute_single` service — no new transport, no feature gate, fuzzed by `fuzz_security_attrs`. A device implementing none of the objects reports `targetSupportsCipSecurity: false`, never an error. | Reading the target's posture makes Phase-1 TLS *operable* (an operator sees whether the device requires client certs, which suites it allows, its cert state) and is cheap: pure decoding over the existing generic services (the objects are reachable over plaintext or TLS). The typed-refusal pattern (unavailable ≠ error) mirrors `sb/browse`. Validated against the OpENer `CIPSecurity` branch (independent implementation of 0x5D/0x5E/0x5F). DESIGN-cip-security.md §4.1. |
| **D-EIP-23** | **CIP Security Phase 2b — vault-native managed trust store + client-cert lifecycle / rotation.** `connection.security.ca` gains a **managed trust store**: `trustStore` (a vault secret whose *all retained versions* form the root set — CA-rollover grace) and `list` (several inline `{"$secret": …}` roots), alongside the Phase-1 single-CA styles. A per-instance cert-lifecycle task re-reads the vault every `reloadIntervalSecs` (default 300): on a **rotation** (the client cert and/or a trust-store CA changed) it bumps `certReloads`, emits `cert-rotated`, and reconnects so the next handshake presents the fresh material (the connect path always rebuilds the `ClientConfig` from the current vault) — **no restart**; on the transition into near-expiry (`client.renewBeforeDays`, default 30) it emits `cert-expiring`, into expired `cert-expired`; and it keeps the `certExpiryDays` gauge current. An already-expired client cert is refused at connect (a loud, typed permanent failure) when `checkExpiration` is on. `sb/status.security` gains `trustStore` (anchor summaries), `clientCertSerial`, `clientCertExpiryDays`, and `certReloads`. | Trust and cert lifecycle is what makes hand-provisioned Phase-1 TLS *operable in a real plant PKI*: a CA rollover needs the old+new roots to overlap (the vault's version grace), and a rotated originator cert must take effect without bouncing the component. The pure decisions (rotation detection, expiry thresholds) live in `eip/rotation.rs` and are unit-tested; the driver is the supervisor. (c) **Packed-BOOL read translation, EXPERIMENTAL:** a signal configured `bool` + `arrayCount: N` whose reply declares `DWORD` is translated — element *n* = bit *(n mod 32)* of word *(n / 32)*, **LSB-first** — into a JSON array of exactly N booleans, GOOD. Bits past N in the final word are device padding and are dropped. **N vs tag size:** a controller only declares `BOOL[n]` in multiples of 32, but the configuration may name any N, so `arrayCount: 40` against a `BOOL[64]` tag means "publish the first 40" and needs `ceil(40/32) = 2` words. (d) **Cardinality under translation** (D-EIP-33): the reply must carry exactly `ceil(N/32)` words, and the BAD detail states the counts **in dwords** beside the boolean count that produced them (`expected 2 packed dword(s) for 40 bools, got 1`) — a bare "expected 2, got 1" against `arrayCount: 40` reads as an adapter bug. The untranslated path's check likewise compares against the **configured** count rather than the requested one, which are different numbers exactly when (e) reshaped the request. (e) **Adaptive request shaping:** first contact asks for N elements (the byte-per-element assumption, unchanged); once a reply has declared `DWORD` the session asks for `ceil(N/32)` thereafter. (f) **Writes are NOT adapted:** a write to a tag observed packed is refused before any device I/O with a typed per-entry error naming the tag and the reason (`DeviceError::Permanent`, rendered into the `sb/write` entry's `error`). (g) **The boundary:** a `real` reply to a configured `dint` stays BAD, forever; so does a **scalar** `bool` answered with a `DWORD`; and non-`bool` types get no translation at all. | **Why observation and not configuration.** A `boolFormat` knob would be an operator *asserting* an observable wire fact — the exact failure mode this component spent a remediation round eliminating. The device already states its representation in every reply (`TagReadResult::wire_type`, D-ENIP-4), so the honest design reads it. **Why translation is legitimate here and nowhere else.** "Logix BOOL arrays are multiples of BOOL[32] and are implemented as a DWORD array" (Rockwell 1756-PM020, p. 58); the Read/Write Tag service-parameter table gives BOOL `0x0nC1`/1 byte and DWORD `0x00D3`/4 bytes. A packed word is not a *different type* being substituted for the configured one — it is the same booleans, stored the way the controller stores them, and every bit of the answer is present. A `real` where a `dint` was configured has no such property: nothing in it says the configured contract was met, so adapting it would be inventing data. That line is the whole decision, and it is why the gate is "is this signal a `bool` **array** and is the reply `DWORD`" rather than anything looser. **Why the memory is per-session and lives on the session.** The session is the only layer that both issues the request and sees the declared type; anything above it would drag `enip` types across the `device.rs` seam. Per-session, not per-instance, because a device does not change a tag's storage mid-session but a reconnect may land on a re-programmed controller — so a fresh session re-observes rather than inheriting a belief it cannot re-check. What the surfaces above need travels out per reading as `Reading::observed_type` (a protocol-agnostic type *name*), which the poll loop records on the shared per-instance `Health`; `sb/signals` reads it there because that verb answers **without device I/O** (§7.5) and routing it through the control channel would give a config view a `DEVICE_UNAVAILABLE` failure mode. **Why the first read is adaptive rather than computed.** Whether a packed tag's Read Tag element count is denominated in BOOLs or in DWORDs is answerable only on hardware. The adaptive read sidesteps the question: asking for N converges either way — a BOOL-denominated controller answers `ceil(N/32)` words and the very first read translates; a DWORD-denominated one answers N words, which is a cardinality BAD, and the observation recorded from that same reply makes the next request `ceil(N/32)`. The cost of guessing wrong is one sample, not a permanent failure. **Why writes are refused rather than translated.** A read gets the whole word and every bit in it is the device's current truth. A write does not: setting N booleans inside `ceil(N/32)` words means writing back the bits that were *not* configured, so the only correct form is a masked read-modify-write (or the CIP masked-write service) — and mask semantics are precisely what no physical controller has confirmed. Writing the word as last read would silently republish a stale value for every padding bit, which on a BOOL array is a coil nobody asked to move. **What remains hardware-gated, stated plainly:** the bit order (PM020's layout, read not measured), the packed element-count denomination, and the masked write. The bench cannot settle any of them — cpppo serves BOOL arrays byte-per-element, so the sim exercises only the control path and a green sim proves nothing about the packed one. The packed evidence is unit and duplex-fixture coverage constructing `DWORD` replies. **Scope kept small:** the `enip` crate needed no change (it already decodes `0x00D3` as `CipValue::Dword` and already reports `wire_type`), so there is no matching D-ENIP row; push assemblies are untouched, because a push layout is the adapter's own declared byte map (D-EIP-18) and carries no device type declaration at all. **One documented shape consequence:** a translated `arrayCount: 1` publishes a one-element JSON array, where the byte-per-element path publishes a scalar (the crate collapses a single element, D-EIP-33). The translated side states the declared contract; the collapse on the other side is the pre-existing `arrayCount: 1` quirk and is left alone rather than propagated. |

### 3.2 The loop, and where everything hooks in

```text
  channels; sb/status & the connectivity provider read the shared Health/Paused state.
```

The template's nested connect/poll loops, the single-task write serialization, and the
backoff are **kept**. New: the control channel (pause/resume/repoll/reconnect/read-now travel the
same one-task serialization path as writes), per-group tickers instead of one, and the paused
gate.

**Two ways out of the loop, and they are not the same (D-EIP-27).** A *link* failure is `LinkLost`:
alarm, counters, backoff, reconnect. A *stop* — this instance's cancellation token firing, or its
control channel closing — is `Stopped`: the driver closes the session (UnRegisterSession / class-1
ForwardClose) and the task returns. `Stopped` raises no `device-unreachable`, emits no event, and
never backs off, so a teardown can never look like an unreachable device. Every wait in the ladder —
the connect attempt, the poll/consume select, and the disconnected backoff service
(`serve_control_disconnected`) — selects on the token `biased`-first, so a stop is observed at the
next await rather than after a full backoff window. §10.3 has the budget and the join/abort rule.

**The push variant (`mode: "push"`)** runs the same `run_device` supervisor with the poll loop
replaced by the push engine (`push.rs`): connect = TCP session + class-1 ForwardOpen
(`PushSession::open`); the `tokio::select!` arms become **the IoUpdate event stream** (instead of
group tickers), the write channel (output-assembly field writes), and the control channel. Per
consumed frame: decode fields via the validated layout → per-field change/deadband +
`sampleMs` floor gate → batch → publish (same `publish.rs`). `IoEvent::Lost` (watchdog timeout,
peer close) breaks into the same backoff/reconnect ladder; `paused` gates *publishing only* —
consumption, snapshot updates, and O→T production continue (D-EIP-20). O→T production and
connection liveness live inside the protocol crate (PROTOCOL-DESIGN §8.6–§8.7); the engine only
consumes typed events.

### 3.3 The seam, extended (device.rs)

The two template traits are kept and extended. The boundary rule stands: **a backend knows
protocols; it never imports `edgecommons::uns`, topics, envelopes, or metrics.**

```rust
#[async_trait]
pub trait DeviceSession: Send + Sync {
    /// Read the given configured signals once (a poll group's worth, or an sb/read subset).
    /// Per-signal failure => that signal comes back as a BAD Reading; Err(_) only when the
    /// CONNECTION is broken.
    async fn read_signals(&mut self, signals: &[SignalSpec]) -> Result<Vec<Reading>>;

    /// Write one value (already coerced/validated by the codec) to a signal. Confirmed:
    /// Ok(()) means the device acknowledged the CIP write.
    async fn write_signal(&mut self, signal: &SignalSpec, value: &serde_json::Value) -> Result<()>;

    /// Enumerate device tags (CIP Get Instance Attribute List), one page.
    /// Default impl: Err(DeviceError::Unsupported) — the sim implements it; generic CIP
    /// devices may not.
    async fn browse(&mut self, cursor: Option<String>, max: usize) -> Result<BrowsePage>;

    /// A minimal liveness probe (used by the paused keepalive): cheapest real CIP round-trip
    /// the backend can do (v1: read of the instance's first configured signal).
    async fn probe(&mut self) -> Result<()>;

    /// Close the session. Safe to call twice.
    async fn close(&mut self);
}

pub struct BrowsePage {
    pub tags: Vec<BrowsedTag>,          // { name, type_name, array_dim: Option<u32> (DIMENSIONALITY
                                        //   1..3, not an element count), instance_id: u32 }
    pub next_cursor: Option<String>,    // None => last page
}
```

`DeviceError` gains one variant beyond the template's `Transient`/`Permanent`:
`Unsupported(&'static str)` — "this device/backend does not implement the operation" (browse on
a non-Logix device). It is neither retried nor a link failure.

Changes from the template signature (surfaced deliberately): `read_signals` now takes the signal
list (the template's zero-arg version hid the config inside the session; poll groups and
`sb/read` subsets need parameterized reads), and `write_signal` takes the resolved `SignalSpec`
(the codec needs the type to build the wire value). The sim backend is updated to match.

**The push side of the seam.** `DeviceBackend` gains `open_push(&IoSpec) → Result<Box<dyn
PushSession>>` (poll instances never call it; push instances never call `connect`):

```rust
#[async_trait]
pub trait PushSession: Send + Sync {
    /// The consumed-I/O stream: decoded field updates + connection lifecycle.
    /// The engine owns the receiver; the session owns translation from the transport.
    fn updates(&mut self) -> &mut mpsc::Receiver<IoUpdate>;

    /// Write one output-assembly field (already coerced by the codec). Ok(()) means the
    /// field is set in the producer buffer and will ride the next O→T frame (§7.3 honesty note).
    async fn write_field(&mut self, signal: &SignalSpec, value: &serde_json::Value) -> Result<()>;

    /// Snapshot of the last consumed input assembly (for sb/read while paused/without waiting).
    fn last_input(&self) -> Option<InputSnapshot>;   // decoded fields + received_at + run_mode

    async fn close(&mut self);                       // ForwardClose + socket teardown; idempotent
}

pub enum IoUpdate {
    Up   { o2t_api_ms: u32, t2o_api_ms: u32 },
    Data { fields: Vec<(SignalKey, serde_json::Value)>, run_mode: bool, received_at: Instant },
    Lost { error: DeviceError },                     // watchdog timeout / peer close / IO error
}
```

The boundary rule is unchanged: the backend maps the protocol crate's types (`IoEvent`,
`CipValue`, `EnipError`) into seam types; the engines above the seam never see the `enip` crate.
`browse`/`probe` remain on `DeviceSession` (explicit messaging) — a push instance that is also a
Logix device can still serve `sb/browse` through a short-lived explicit session (§7.5).

### 3.4 The enip backend (eip/) — consuming the owned stack

`eip/` is the only adapter module that imports the `enip` crate, against the **public API pinned
in PROTOCOL-DESIGN §11.2** (implementation agents: that section is the contract — do not
improvise around it):

```rust
use enip::{EipClient, ClientOptions, RoutePath, TagAddress, CipType, CipValue,
           IoManager, IoConnectionSpec, IoEvent, AssemblyLayout, EnipError};

// poll (unconnected default; connected class-3 when connection.connected = true):
let client = EipClient::connect(&endpoint, ClientOptions {
    route: slot.map(RoutePath::backplane_slot),      // absent slot ⇒ None (cpppo/CompactLogix)
    connect_timeout, request_timeout,                // from §4.1 timeouts
    connected_messaging: cfg.connection.connected,
    ..Default::default()
}).await?;
let r = client.read_tag(&TagAddress::parse(&spec.tag_path)?, spec.array_count.unwrap_or(1)).await?;
/// r.wire_type is the OBSERVED representation (D-EIP-35): remembered per tag (it shapes the next
// request), reported as the reading's observedType, translated when it is a representation variant
// of the configured type (packed BOOL array ⇒ DWORD), else compared — mismatch ⇒ BAD
// ("DECODE type mismatch (expected …, device declares …)")
client.write_tag(&addr, spec.eip_type.into(), &coerced).await?;   // Ok = CIP-acked (confirmed)

// push:
let io  = IoManager::bind("0.0.0.0:0").await?;   // one per push session; ephemeral source port
let conn = io.forward_open(&client, spec.io_connection_spec()).await?;  // from §4.6 config
conn.set_output(&initial_output)?;  conn.set_run(true);
// conn.events() → IoEvent::{Up, Data, Lost} → translated to IoUpdate via the AssemblyLayout
```

- **Timeouts and correlation live in the crate** (per-request deadlines, stale-reply quarantine,
  class-1 watchdog — PROTOCOL-DESIGN §10); the adapter maps `EnipError` → `DeviceError` using
  `EnipError::is_transient()` as the default, overridden per §10.1's table.
- **Typed decode**: `read_tag` returns the wire-declared `CipValue`; `eip/types.rs` converts to
  JSON per the configured `EipType`, **translates a representation variant of that type** into it
  (D-EIP-35), and flags anything else as a BAD sample naming both declarations (never a decode
  panic — the crate guarantees totality, D-ENIP-4).
- **Each push session owns its own `IoManager`**, bound to an ephemeral UDP source port
  (`0.0.0.0:0`) and advertised to the target in the ForwardOpen's Sockaddr Info items (§11.2
  finding 1). `2222` is the *target's* destination port, never a listening port on the adapter.
- One request per signal per cycle in poll mode (D-EIP-15).
- The `AssemblyLayout` for a push instance is built **once at startup** from §4.6 config;
  construction validates every field against the assembly size, so a bad offset is a config
  error at start, not a runtime surprise (D-EIP-18).

| `publishMode` | onChange \| always, default from device ▸ global | Per-group publish gate. |
| `signals[]` | array, required, min 1 | See §4.4. |

### 4.4 Signal (`$defs/signal`)

| Key | Type / default | Meaning |
|---|---|---|
| `name` | string, required, lower-kebab (UNS-token pattern) | Human label AND the `data` topic channel (§6.1). Unique per device. |
| `tagPath` | string, required | The CIP tag path, verbatim/case-sensitive (`"LINE_SPEED"`, `"Program:Main.FillPV"`). It IS the stable `signal.id`. Unique per device. |
| `type` | enum, required | `bool, sint, usint, int, uint, dint, udint, lint, ulint, real, lreal` (§5.2). Required — CIP decode is typed. |
| `arrayCount` | int 1–65535, optional | Present ⇒ the signal is a 1-D array read of that many elements (`read_tag(&tag, count)`); value is a JSON array. The bound is the CIP Read Tag `u16` element count; out of range is a validation error, never a clamp (D-EIP-33). With `type: bool` the signal is accepted and warned as **experimental** (D-EIP-16). |
| `scale` | number, optional | Published value = `raw * scale + offset` (element-wise for arrays; numeric types only). |
| `offset` | number, optional | See `scale`. |
| `deadband.type` | `none` \| `absolute` \| `percent`, **none** | Modbus-identical semantics (`none`: any change republishes; `absolute`: `\|new−old\| ≥ value`; `percent`: relative to old). Non-numeric ⇒ any change. Arrays: exceeded if ANY element exceeds. |
| `deadband.value` | number ≥ 0, **0** | Threshold. |

**Precedence (normative):** signal/field ▸ poll group (poll only) ▸ device `defaults` ▸
`global.defaults` ▸ built-in default. Validation is fail-fast at startup per device (a malformed
device is skipped with a warning, template behavior kept; a component with zero valid devices
refuses to start). Additional startup validations: duplicate `name`/`tagPath` within a device;
`writes.allow[]` entries that match no configured `tagPath` (poll) / no output field id (push)
log a warning (they may be intentional for `sb/write`-by-explicit-ref, §7.2 — warned, not
rejected); `scale`/`deadband` on `bool` rejected; `arrayCount` outside `1..=65535` rejected
(D-EIP-33). `arrayCount` on a `bool` signal is **warned, not rejected** — one WARN per signal, from
the same returned-warnings channel as the `writes.allow[]` ghosts (D-EIP-16).

## 5. Signal & data-type model

### 5.1 CIP → JSON value mapping

| Config `type` | CIP type (code) | Rust decode | JSON value | Write accepts |
|---|---|---|---|---|
| `bool` | BOOL (0xC1) | `bool` | `true`/`false` | JSON boolean |
| `sint` | SINT (0xC2) | `i8` | number | integral number in range |
| `usint` | USINT (0xC6) | `u8` | number | integral number in range |
| `int` | INT (0xC3) | `i16` | number | integral number in range |
| `uint` | UINT (0xC7) | `u16` | number | integral number in range |
| `dint` | DINT (0xC4) | `i32` | number | integral number in range |
| `udint` | UDINT (0xC8) | `u32` | number | integral number in range |
| `lint` | LINT (0xC5) | `i64` | number | integral number in range |
| `ulint` | ULINT (0xC9) | `u64` | number | integral number in range |
| `real` | REAL (0xCA) | `f32` | number | any JSON number |
| `lreal` | LREAL (0xCB) | `f64` | number | any JSON number |

- **Arrays** (`arrayCount: N`): poll reads request N elements (`read_tag(&tag, N)`); push fields
  extract N contiguous elements from the assembly. The JSON value is a JSON array of N elements,
  each per the row above (`SOUTHBOUND.md` §2 value-typing rule).
  A write to an array signal accepts a JSON array of exactly N elements, each coerced to the
  element type; length mismatch is a per-entry write failure (`"expected N elements"`).
  **N is bounded to `1..=65535`** — the CIP Read Tag element count is a `u16` — and the bound is a
  refusal, never a clamp: an out-of-range `arrayCount` is a config-validation error, and in an
  `sb/read`/`sb/write` explicit ref a `BAD_ARGS` refusal (D-EIP-33). **N is also a promise the reply
  must keep**: the poll path compares the elements a read returned against the **configured** count
  (which is also the requested one, except on a reshaped packed-BOOL read — D-EIP-35), and a
  mismatch is a BAD sample naming expected vs got, not a short array published GOOD. A
  reply of one element decodes as a scalar (the protocol crate derives the count from the payload
  length), which is what satisfies `arrayCount: 1` and what makes a one-element answer to
  `arrayCount: 8` a mismatch rather than a GOOD scalar.
- **`bool` arrays are EXPERIMENTAL** in poll mode (D-EIP-16, D-EIP-35). `{"type": "bool",
  "arrayCount": N}` is accepted, and the adapter reads **whichever representation the device
  declares**: byte-per-element (`0xC1`) or the Logix `DWORD` packing (`0x00D3`, 1756-PM020),
  unpacked LSB-first — element *n* is bit *(n mod 32)* of word *(n / 32)* — into a JSON array of
  exactly N booleans. N words: `ceil(N/32)`, with bits past N in the final word dropped as device
  padding; a reply of any other word count is a BAD sample naming the counts in dwords. The
  representation is observed per tag, never configured, and reshapes the following read. A **write**
  to a tag observed packed is refused (it needs a masked read-modify-write). Each such signal raises
  one validation WARN: the packed path is unvalidated against physical hardware, and the bit order
  and packed element-count denomination await a real controller — the adapter has no device-family
  detection, so the label is global to the feature. Scalar `bool` and push assembly `bool` array
  fields are unaffected.
- **Exact integers on write.** "Integral number in range" means the integer the caller sent, not its
  nearest `f64`. With no value transform (`scale`/`valueOffset` absent, or spelled as the identity
  `1.0`/`0.0`) a JSON **integer literal** written to an integer type is range-checked against that
  type's exact bounds and carried to the device through `i64`/`u64`, never through an `f64` — so a
  `ulint` of `9007199254740993` or an epoch-nanosecond `lint` lands bit-for-bit, mirroring the read
  path's native-integer precision. A JSON **float** is accepted for an integer type when it is finite
  and integral (`5.0` for a `dint`); a fractional one is refused. Because the bounds are exact, a
  value one past `lint`/`ulint`'s maximum is refused rather than saturated. Where a **real** transform
  applies the arithmetic is unavoidably `f64`, so an integer input beyond ±2⁵³ is a per-entry failure
  naming the value, never a silent rounding.
- **scale/offset** (numeric only): read: `published = raw * scale + offset` (f64 arithmetic;
  the published JSON number is f64). Write: `device = (value - offset) / scale`, then
  range-checked and coerced to the CIP type; out-of-range ⇒ per-entry failure, never a clamp.
  Element-wise for arrays.
- **Rejected at config validation** (D-EIP-16): `string`, structures/UDTs, multi-dimensional
  arrays. The simulator's `RECIPE=SSTRING` tag exists precisely to prove the adapter's
  validation/browse story for unsupported types (§11.1).

### 5.2 Stable identity split (`SOUTHBOUND.md` §2)

| Contract field | Poll mode | Push mode |
|---|---|---|
| `device.adapter` | `"ethernet-ip"` (`"sim"` for the simulator backend) | same |
| `device.instance` | the instance id (`"filler-plc"`) | same (`"palletizer-io"`) |
| `device.endpoint` | `connection.endpoint` (`"127.0.0.1:44818"`) | same |
| `signal.id` | the `tagPath`, verbatim — e.g. `"LINE_SPEED"`, `"Program:Main.FillPV"` (D-EIP-9) | `a<assemblyInstance>/<offset>/<type>[.<bit>]` — e.g. `"a100/0/bool.0"`, `"a100/4/udint"` (D-EIP-18) |
| `signal.name` | the config `name` (`"line-speed"`) | same (`"motor-run"`) |
| `signal.address` | `{ "tagPath": "ZONE_TEMPS", "type": "real", "arrayCount": 8, "slot": 0 }` — optional keys only when configured | `{ "assembly": 100, "offset": 0, "type": "bool", "bit": 0, "arrayCount": 7, "slot": 0 }` — optional keys only when configured |
| `samples[]` | one per publish; batched under `batchMs` (§6.2) | same |

`signal.address` is the protocol-native round-trip object: everything needed to re-address the
value (tag path + decode type + array length + routing slot for poll; assembly instance + byte
offset + type + bit for push). Both id forms are derived from real, restart-stable addressing —
there is no volatile-index problem here (unlike OPC UA `ns=`), so id and address agree by
construction. The push id mirrors Modbus's `u<unit>/<table>/<addr>/<type>` shape.

### 5.3 Topic channel vs id

The `data` topic channel is the config **`name`** (lower-kebab, already a valid UNS token), set
explicitly via `SignalUpdateBuilder::signal_path(name)`. The raw `tagPath` (with `:`, `.`,
uppercase) rides only in the body (`signal.id`), untouched. This keeps topics clean without
lossy sanitization of the id (the facade would otherwise sanitize the id into the channel).

### 5.4 Quality mapping (`SOUTHBOUND.md` §3)

| Normalized | Condition (poll) | Condition (push) | `qualityRaw` |
|---|---|---|---|
| `GOOD` | CIP read succeeded, value decoded | field decoded from an accepted frame with run-mode `Run` (or no O→T header semantics apply) | `"0x00"` (CIP general status Success) |
| `BAD` | CIP error response for THIS tag (e.g. path segment error 0x04/0x05 = tag not found; service not supported 0x08; insufficient data 0x13), or decode/type mismatch | — (a mis-sized/malformed frame is dropped+counted by the stack, never decoded into samples) | the typed `CipStatus` rendering, e.g. `"0x04 (path segment error)"`; decode failures `"DECODE <detail>"` |
| `BAD` | per-request timeout that did NOT break the session (isolated) | — | `"TIMEOUT"` |
| `UNCERTAIN` | value decoded but the scale/offset produced a non-finite number (NaN/inf) | same | `"NON_FINITE_AFTER_SCALE"` |
| `UNCERTAIN` | — | frame accepted but the peer signals **Idle** in the run/idle header (values present, process not running) | `"IDLE"` |

A BAD sample's `value` is JSON `null`. Connection-level failures (socket errors, RegisterSession
loss, repeated timeouts — poll; class-1 watchdog timeout / `IoEvent::Lost` — push) are NOT
samples — they break the engine loop into reconnect (§10), and the signals' staleness accounting
takes over.

`serverTs`: poll = adapter read time (facade default, injected clock); push = the frame's
`received_at`, so batched samples keep their true arrival times. `sourceTs` never emitted in
either mode — neither explicit replies nor class-1 frames carry a device timestamp (D-EIP-11).

### 6.2 The `SouthboundSignalUpdate` publish path (exact facade sequence)

Per changed signal per publish flush (verified against `facades/data.rs` /
`facades/signal_update.rs` at the pinned rev):

```rust
let mut sample = Sample::with_quality(value, quality);       // Quality::{Good,Bad,Uncertain}
sample = sample.quality_raw(raw);                            // ALWAYS set (never rely on the
                                                             // "unspecified" default marker)
// batching: additional Samples get an explicit .server_ts(read_iso) so a coalesced batch
// preserves per-read times; the newest sample may leave server_ts to the facade default.

let update = data.signal(&spec.stable_id)       // poll: tagPath (D-EIP-9); push: a<inst>/<off>/<type> (D-EIP-18)
    .name(&spec.name)
    .address(spec.address_json())               // §5.2 object
    .device_parts("ethernet-ip", &cfg.id, &cfg.connection.endpoint)
    .signal_path(&spec.name)                    // topic channel = name (§5.3)
    .samples(batch)                             // 1..N samples (batchMs window)
    .build();
data.publish(update).await?;                    // header SouthboundSignalUpdate/1.0, identity
                                                // stamped, topic minted — all facade-owned
```

- **Batching**: with `batchMs > 0`, samples for one signal are buffered and flushed when the
  window closes (per-signal windows, opened by the first buffered sample). `publishMode:
  onChange` gates *entry into* the buffer (deadband); `always` buffers every poll. A BAD sample
  always passes the gate (a failure is information). The onChange baseline the gate compares
  against is the `committed ∪ pending` pair of D-EIP-32 (§7.4): a gated-in value is *pending*
  until its publish is confirmed, at which point it becomes *committed*; a failed publish drops
  it so the value is retried rather than suppressed. An open window is discarded on pause, never
  flushed or held.
- **Publish latency**: wall time of the `data.publish().await` call, recorded into
  `southbound_health.publishLatencyMs` and `EtherNetIpPublish.publishLatencyMs`.
- Channel routing (local ▸ config `publish.channel` ▸ per-call `via`) is left at the facade
  default (LOCAL); the config passthrough works without adapter code if a deployment sets
  `publish.channel`.

## 7. Command surface

All verbs are registered on the component's `CommandInbox` (`gg.commands()`), advertised by the
built-in `describe`, and are **request/reply** (a fire-and-forget request still executes; the
reply is dropped by the inbox). The library-owned built-ins (`ping`, `describe`, `status`,
`reload-config`, `get-configuration`) come for free and are not re-implemented.

**Instance routing (D-EIP-13 + D-EIP-26):** every verb declares `CommandScope::Instance`, so the
library resolves the addressing before dispatch: an instance-addressed delivery topic
(`…/{instance}/cmd/{verb}`, SOUTHBOUND §2.2) names the device, a component-scoped delivery names it
with `"instance": "<id>"` in the body, and a body `instance` that conflicts with the topic token is
refused with `BAD_ARGS` before the handler runs. What stays adapter-side is the configuration-dependent
half: an unaddressed request routes to the sole **running** device, with ≥ 2 of them it is `BAD_ARGS`,
with none of them (the stop stage of a restart-all configuration change, §10.4) it is
`DEVICE_UNAVAILABLE` — addressing one would only earn a `NO_SUCH_INSTANCE` — and an addressed instance
that is not running is `NO_SUCH_INSTANCE`. Replies always include the resolved `"id": "<instance>"`.

**Error codes** (reply `{"ok":false,"error":{"code","message"}}` via `CommandError`):
`BAD_ARGS`, `NO_SUCH_INSTANCE`, `WRITE_NOT_ALLOWED`, `WRITE_FAILED`, `DEVICE_UNAVAILABLE`
(device task gone / channel closed, or no instance running at all), `READ_FAILED` (connection-level failure during an on-demand
read), `RECONNECT_FAILED`, `BROWSE_UNSUPPORTED`, `BROWSE_FAILED`, `PAUSED` (a whole operation the
paused state prohibits — `repoll`, §7.4.7). Per-entry problems inside batch read/write are
reported inline in the result, not as command errors.

### 7.1 `sb/status` — instance status

Request: `{ "instance"? }` →

```json
{ "id": "filler-plc", "mode": "poll", "connected": true, "state": "ONLINE", "paused": false,
  "endpoint": "127.0.0.1:44818", "adapter": "ethernet-ip",
  "metrics": { "read": { "interval": 412, "total": 15230 },
               "write": { "interval": 1, "total": 12 },
               "readErrors": { "interval": 0, "total": 3 } },
  "security": { "mode": "plaintext" } }
```

The `security` object (D-EIP-21, DESIGN-cip-security.md §3.4) is always present so a console can render
the posture column unconditionally. A TLS instance reports the negotiated facts:
`"security": { "mode": "tls", "tlsVersion": "1.3", "cipherSuite": "TLS13_AES_128_GCM_SHA256",
"peerVerified": true, "peer": "…", "clientCertNotAfter": "2027-03-01T00:00:00Z",
"handshakeFailures": { "interval": 0, "total": 0 } }`. The `state` keepalive carries the same posture
as `attributes.security` (`"tls"`|`"plaintext"`), and `EtherNetIpConnection.tlsHandshakeFailures`
(§8.2) counts handshake failures.

**Managed trust store + cert lifecycle (Phase 2b, D-EIP-23).** A TLS instance additionally carries the
adapter's own client-cert lifecycle facts and the managed trust store:
`"clientCertSerial": "0A1B2C", "clientCertExpiryDays": 400,
"trustStore": { "count": 2, "anchors": [ { "subject": "CN=Plant Root CA", "notAfter": "…" }, … ] },
"certReloads": { "interval": 0, "total": 1 } }`. `trustStore.count` is the number of trust anchors
sourced (a CA rollover shows both the old and new roots while both are live); `certReloads` counts
rotations picked up from the vault without a restart; `clientCertExpiryDays` mirrors the
`EtherNetIpConnection.certExpiryDays` gauge (§8.2).

**EST enrollment (Phase 2c, D-EIP-24).** When `est.enabled`, the TLS instance's `security` object also
carries an `est` sub-object with the enrollment lifecycle state:
`"est": { "enabled": true, "server": "https://est.plant.example:8443/.well-known/est",
"lastEnroll": "2026-07-19T12:00:00Z", "nextRenew": "2027-05-02T00:00:00Z", "lastError": null,
"enrollments": 1, "failures": 0 }`. `nextRenew` is `notAfter − renewBeforeDays`; `enrollments`/`failures`
mirror the `EtherNetIpConnection.estEnrollments`/`estFailures` measures (§8.2).

**Target posture (Phase 2a, D-EIP-22).** Whenever a session is up (either mode), `security` also
carries `targetSupportsCipSecurity` (bool) and, when the device implements the CIP Security objects, a
`target` sub-object with the decoded posture:
`"target": { "state": "Configured", "profiles": ["EtherNet/IP Confidentiality"],
"allowedCipherSuites": ["TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256"], "availableCipherSuites": [...],
"verifyClient": true, "sendCertificateChain": true, "checkExpiration": true, "pullModel": false,
"certificate": { "pushSupported": true, "pullSupported": false, "name": "…", "state": "Verified",
"encoding": "PEM" } }`. A generic CIP device (e.g. cpppo) reports `targetSupportsCipSecurity: false`
and no `target`.

A push instance answers the same shape plus an `io` object:
`"io": { "o2tApiMs": 100, "t2oApiMs": 100, "run": true, "peerRun": true,
"framesConsumed": {...}, "staleDropped": {...}, "sequenceGaps": {...}, "sendErrors": {...},
"recvErrors": {...}, "refusedRedirects": {...} }` (negotiated APIs from the ForwardOpen reply,
run/idle both directions, and the §8.8 counters as `{interval, total}` pairs).

`connected`/`state`/`paused` come from the SAME shared Health/Paused state the connectivity
provider reads — ask or watch, same answer. (The universal `status` built-in already returns
`instances[]`; `sb/status` is the southbound-detail superset for one instance.)

### 7.2 `sb/read` — on-demand batch read

Request: `{ "instance"?, "signals": [ <signal-ref>, … ] }` where **`<signal-ref>`** is
`{"name": "<configured name>"}` (friendly) **or** `{"tagPath": "...", "type": "<EipType>",
"arrayCount"?}` (explicit, for tags not in config — the Modbus explicit-ref analog). Reply:

```json
{ "id": "filler-plc", "reads": [
    { "signal": { "id": "LINE_SPEED", "address": { "tagPath": "LINE_SPEED", "type": "real" } },
      "value": 54.9, "quality": "GOOD", "qualityRaw": "0x00",
      "serverTs": "2026-07-18T12:00:00Z" } ] }
```

Reads reuse the §5 value/quality encoding exactly (`SOUTHBOUND.md` §2.2). Unresolvable refs come
back as entries with `"quality":"BAD"`, `"qualityRaw":"UNRESOLVED_REF"` — but an explicit ref whose
`arrayCount` is not an integer in `1..=65535` is a malformed *argument*, not an unresolvable ref, and
refuses the whole command with `BAD_ARGS` naming the bound (D-EIP-33; the same rule guards §7.3's
write refs, so no partial batch is written under one). Reads are serviced by
the device task (a `ReadNow` control message carrying a oneshot reply), so they serialize with
the engine loop — and they work while paused. On-demand reads are **not** published to `data`.

**Push instances:** `sb/read` answers from the **last consumed input snapshot**
(`PushSession::last_input`) — no device round-trip exists for "read one field now" in implicit
I/O. Each entry's `serverTs` is the snapshot's receive time; if the connection is down or no
frame has arrived yet, entries answer `"quality":"BAD"`, `"qualityRaw":"NO_FRAME"`. The explicit
push ref form is `{"assembly": 100, "offset": 4, "type": "udint", "bit"?, "arrayCount"?}` —
resolved against the configured layout only (arbitrary offsets outside the declared
`sizeBytes` are `UNRESOLVED_REF`; the layout is the contract).

### 7.3 `sb/write` — confirmed, allow-listed batch write

Request: `{ "instance"?, "writes": [ { <signal-ref>, "value": <any> }, … ] }` (a single object
without the `writes` wrapper is also accepted, per §2.2). Reply:

```json
{ "id": "filler-plc", "written": 1, "results": [
    { "signal": "FILL_SETPOINT", "value": 55.5, "ok": true },
    { "signal": "MOTOR_SPEED", "ok": false, "error": "not in writes.allow" } ] }
```

Normative gate order, per entry: resolve ref → **allow-list check against the stable
`signal.id`** (tagPath or push field id; refusal = inline `ok:false` + a `write-audit` Warning
event; the whole command errors `WRITE_NOT_ALLOWED` only when ALL entries are refused) → codec
coercion (§5.1; failure inline) → the write travels the device task's write channel (template
`WriteRequest` kept, extended to carry the `SignalSpec`) → **confirmed**: `ok:true` only after
the CIP reply. Every entry is audited on `evt` (§6.3). An explicit-ref write is still matched
against `writes.allow[]` by its id — the allow-list gates identity, not config membership.

**Push instances** write **output-assembly fields** (input fields are never writable — refusal
`"error": "input field"`). Confirmation honesty (stated verbatim in user docs): implicit I/O has
no per-write device acknowledgment; `ok:true` means *the field is set in the O→T producer buffer
and rides every subsequent cyclic frame* (`PushSession::set_output`).

That claim is **confirmed, not assumed** (D-EIP-31). The verdict travels the whole chain and back —
session handle → translator task → the `enip` I/O manager's `stage_output_by` ack → back — so
`ok:true` asserts that the I/O manager holds this buffer for a **live** class-1 connection. Staging
that cannot be confirmed is an inline `ok:false` naming the reason, with the usual `write-audit`
Warning, never a success:

| Push write refusal | `error` | Cause |
|---|---|---|
| session closing | `push session is closing; output not staged` | the translator's control channel is gone (the session was closed) |
| handoff unaccepted | `the push translator did not accept the write within the request timeout; output not staged` | the translator did not read its control channel for a whole `requestTimeoutMs` (its queue is full of commands it has not reached). A cancelled handoff took no queue slot, so nothing is left to land later |
| translator ended | `push translator ended before the output was staged` | the class-1 link was lost / the task exited between the handoff and the verdict |
| unconfirmed | `output staging was not confirmed within the request timeout` | the translator could not answer inside `requestTimeoutMs` (e.g. wedged on a full update channel) |
| expired before staging | `the request timeout elapsed before the output was staged` | the request outlived the write's budget while queued, and was dropped rather than staged — the verdict the *abandoned* command produces |
| connection lost | `class-1 connection lost (<reason>); output not staged` | the I/O manager removed the connection because it was lost — `<reason>` is the same wording the seam's `Lost` carries (watchdog timeout, peer close, socket error) |
| connection closed | `the class-1 connection was closed; output not staged` | the I/O manager no longer holds the connection, and no loss preceded it: it was closed, or the manager task itself has stopped |

**The whole write is bounded, and a refusal is final.** One absolute deadline derived from
`timeouts.requestTimeoutMs` covers the control handoff, the wait for the verdict, and the staging
decision itself, so a write cannot outlive the operator's own per-request number whatever the queue
in front of it is doing. That deadline is carried *in* the command: the translator, and then the I/O
manager at the only place that mutates the producer buffer (D-ENIP-20), drop an expired request
instead of staging it, and the session's output image is adopted only once the manager has taken it.
So a value reported `ok:false` never appears in a later O→T frame — neither on its own, nor carried
out inside the next accepted write.

The last two rows are one refusal from the protocol crate's side — `EnipError::Closed`, whose
`Display` is the bare word `"closed"` — split by the adapter, because a device fault and an orderly
stop demand different operator responses. Both are **`Transient`**: the reconnect ladder recovers a
lost and a closed class-1 connection alike. Every other staging error keeps `map_enip_error`'s own
classification (a mis-sized buffer stays `Permanent`).

The reply carries `"applied": "next-frame"` on push entries so consoles can render the distinction
from poll's CIP-acked writes.

### 7.4 `sb/pause` / `sb/resume` — the contract extension (D-EIP-3, D-EIP-14, D-EIP-32)

Request: `{ "instance"? }`. Replies: `{ "id", "paused": true|false, "changed": true|false }` —
**idempotent** (pausing a paused instance is `changed:false`, never an error).

Normative pause semantics — **per-instance, mode-uniform: pause suspends the instance's
*telemetry production* (its `data` publishes), whether it polls or consumes push I/O** (user
clarification; D-EIP-14 + D-EIP-20):

1. **No `data` publishes occur while paused.** Poll: scheduled poll ticks are gated OFF (all
   groups). Push: consumed frames are NOT published — but consumption itself continues (the
   snapshot, sequence validation, and connectivity stay live). This holds across the pause edge
   too: **open `batchMs` coalescing windows are DISCARDED at pause** (D-EIP-32) — their buffered
   samples are dropped and the `pending` baselines those samples carried are cleared, since
   nothing was published. Flushing them at pause time would publish through an instance that is
   going quiet; holding them would release a stale burst the moment it resumes (and on push that
   burst lands *after* the §7.4.8 rebase, see 8). Discard is the only semantics with zero stale
   publishes; an operator who pauses forfeits at most `batchMs` of buffered telemetry. A paused
   loop therefore has no batch deadline to wake for, and no window survives to flush on resume.
2. The **session/connection stays open**. Poll: the explicit session. Push: the class-1
   connection — O→T production continues at the API (heartbeat/outputs, run/idle unchanged;
   stopping would make the *target* time us out, D-EIP-20). `sb/read`, `sb/write`, `reconnect`,
   `sb/browse` still work.
3. `connected` stays truthful via real I/O. Poll: a **keepalive probe** (`DeviceSession::probe`,
   cadence `healthThresholds.keepaliveProbeIntervalMs`) since no polls flow; a probe failure
   drives the normal reconnect path (still paused after reconnecting). Push: **no probe needed**
   — T→O reception and the watchdog already are the liveness signal.
4. Reflection — the surfaces move together: (a) `state` keepalive `instances[]`: `state`
   token becomes **`"PAUSED"`**, `attributes.paused: true` (`connected` stays truthful);
   (b) events: `adapter-paused` / `adapter-resumed` (§6.3); (c) `sb/status` reports
   `paused: true`. The transition also flushes `southbound_health` immediately (§8.7); there is
   no `paused` measure — the metric carries exactly the eight SOUTHBOUND §5 measures (§8.1).
5. Staleness accounting is **suspended** while paused (§9.3) — a paused signal is paused, not
   stale.
6. Pause state is in-memory; restart ⇒ production resumes (documented in `docs/`).
7. `repoll` against a paused instance is refused with the dedicated top-level code **`PAUSED`**
   (`"instance is paused - resume first"`) — an explicit one-shot read is what `sb/read` is for.
8. On resume, push change-detection state is **re-based to the current snapshot** so the paused
   span's accumulated drift is not published as one giant "change" burst; poll behaves likewise
   via its per-signal last-published values. The rebase sets each field's `committed` baseline to
   its current value and clears `pending` — and because 1 discarded the open windows, nothing
   pre-pause survives to flush over the top of it.

**The baseline the pause rules act on (D-EIP-32).** Both engines carry a two-part onChange
baseline per signal: `committed`, the last value whose publish the facade **confirmed**, and
`pending`, the latest value gated in but not yet confirmed (in flight, or sitting in an open
`batchMs` window). The gate suppresses a value matching *either* — the `pending` half is what
keeps a poll interval shorter than `batchMs` from enqueuing a duplicate sample for an unchanged
reading — and a newer, different value simply replaces `pending`, both samples staying in the
batch. A confirmed publish promotes `pending` into `committed`; a **failed** publish drops
`pending` and leaves `committed` where it was, so the same value gates in again on its next
occurrence and is retried instead of being suppressed against something that never reached the
bus (the log line and `EtherNetIpPublish.publishFailuresTotal` are unchanged). Quality semantics
are untouched: BAD/UNCERTAIN bypass the gate, and never become a baseline. `publishMode: always`
consults no baseline and is unaffected. Pause clears the `pending` half along with the windows
it discards (1); resume re-bases the `committed` half (8).

> **Contract note (surfaced deliberately):** `sb/pause`/`sb/resume` extend beyond
> `SOUTHBOUND.md` §2.2 and beyond both reference adapters. They are designed here as a
> general poll-adapter convention and are a candidate for promotion into core `SOUTHBOUND.md`
> (a core-repo change, out of scope for this work — do NOT edit core here).

### 7.5 The rest of the family

| Verb | Request | Reply / behavior |
|---|---|---|
| `sb/signals` | `{ "instance"? }` | `{ "id", "mode", "signals": [ { "name", "id", "address", "pollGroup"?, "pollIntervalMs"?, "direction"?, "publishMode", "writable": bool, "deadband"?, "observedType"? } ] }` — the resolved config view, `writable` = allow-list membership. Poll entries carry `pollGroup`/`pollIntervalMs`; push entries carry `direction: "input"\|"output"` instead. `observedType` is the wire type the device declared on that poll signal's **last reply** (`"REAL"`, `"DWORD"`, `"UNKNOWN(0xNNNN)"`), **absent until first contact** and absent on push entries, which decode the adapter's own byte map (D-EIP-35). No device I/O — it reads the shared per-instance state the poll loop records. |
| `sb/browse` | `{ "instance"?, "cursor"?, "max"? (default 200, cap 1000) }` | Paged discovery, one page per request, same reply shape in both modes: `{ "id", "tags": [ … ], "cursor"? }`, `cursor` present only while entries remain. **Poll** = CIP tag discovery via Get Instance Attribute List (`EipClient::list_tags`), tags `{ "name", "type", "arrayDim"?, "configured": bool, "supported": bool }` (`configured` marks tags already in config; `arrayDim` is the array **dimensionality** the typed SymbolType declares — `1` for a 1-D array, `2`/`3` for a multi-dimensional one, absent for a scalar — never an element count, which a symbol type word cannot carry; `supported` = configurable and decodable per §5.1, which is the type name **and** the shape — structs, strings and multi-dim (`arrayDim > 1`) report `false`; 1-D arrays of the elementary types report `true`, including 1-D `BOOL`, which is configurable as an experimental signal (D-EIP-16), D-EIP-33). **Push** = the configured assembly layout (§4.6), tags `{ "name", "id", "type", "direction", "configured": true, "supported": true }` (a configured layout field is by construction both), no device round-trip. Works for push instances against a Logix-family device too when the tag list is what is wanted (a short-lived explicit session); devices without the tag service ⇒ `BROWSE_UNSUPPORTED`; mid-browse failures ⇒ `BROWSE_FAILED`. **Cursor contract (both modes):** the cursor is opaque to clients — pass back the previous page's value verbatim. Poll cursors are decimal symbol-instance resume points carried at full `u32` width (PROTOCOL-DESIGN §7.3 / D-ENIP-19); push cursors are decimal indexes into the flat field list (inputs in declaration order, then outputs). A request with no cursor starts the poll walk at symbol instance **0** and the push walk at index 0 — both at the bottom of their space, so an entry that sits there is enumerated rather than skipped. `max` is honoured truthfully: when a device page exceeds `max` the reply is cut to `max` and the cursor resumes from the **last record actually returned**, so a client that follows cursors sees every tag exactly once. A cursor the adapter cannot read is refused rather than restarted from the top — poll: `BROWSE_FAILED` naming the cursor; push: `BAD_ARGS` (the command layer owns that cursor format, so it can be precise). **Hierarchical panel mode:** presence of `"ref"` selects the `treeBrowser` form over the SAME inventory (poll: the device tag list; push: the configured assembly layout) — `{ "ref", "depth"? (clamp 1..4), "maxRefs"? (clamp 1..1000) }` → `{ "id", "mode": "hierarchical", "root": { nodeId, name, nodeClass, dataType, refs[] }, "refCount", "depth", "truncated" }`; `"root"` is the device node whose `contains` refs are the inventory, a tag/field id is a leaf, an unknown ref is `BAD_ARGS`. Mixing `ref`/`depth`/`maxRefs` with `cursor`/`max`, or `depth`/`maxRefs` without `ref`, is `BAD_ARGS`. This is the one form the adapter drives to completion, so its termination is the adapter's own property, not the backend's: a backend cursor that does not advance past the one already followed, one that is not a number, and a walk past `MAX_BROWSE_PAGES` (1024) are each `BROWSE_FAILED` rather than a handler that never returns. |
| `reconnect` | `{ "instance"? }` | Drop + re-establish, one bounded attempt (control message to the device task): poll = session re-register; push = ForwardClose + ForwardOpen. `{ "id", "connected": bool }`; failure ⇒ `RECONNECT_FAILED` (the task then continues normal backoff). Works while paused (does not resume). |
| `repoll` | `{ "instance"? }` | Poll instances only: force an immediate poll of ALL groups now: `{ "id", "polled": <signals read> }`. Refused while paused with `PAUSED` (§7.4.7); refused for push instances with `BAD_ARGS` (`"push instance - data arrives cyclically"`). |

## 8. Metrics

All defined via `MetricBuilder::create(name).with_config(&config).add_measure(...)
.add_dimension(...)` and emitted through the injected `Arc<dyn MetricService>` — destination is
config-driven (`metricEmission.target`), no adapter code per target. Units are `Count`,
`Milliseconds`, `None`; resolution 1 (high) only for live gauges, else 60.

**Conventions (normative):**
- Every **counter** is a measure PAIR: `<name>Total` (monotonic since component start) and
  `<name>Interval` (since the previous emit of that family; reset on emit). The OPC UA pair
  spelling over the Modbus family/dimension structure — D-EIP-12.
- **Gauges** (`connectionState`, `sessionConnected`, `signalsSubscribed`, `batchSize`, latencies,
  inventory sizes) are single measures.
- Dimensions are **low-cardinality only**: `instance`, `pollGroup`, `result`
  (`success`|`error`), `verb` (closed set §8.6), `publishMode` (`onChange`|`always`),
  `connectionMode` (`connected`|`unconnected`). **Never** tag names, signal ids, addresses,
  endpoints, or error text. (`coreName`/`category`/`component` are injected by the builder.)
- One metric definition per (family × dimension combination), defined at startup like Modbus
  (`_define_*`), values accumulated in atomics/mutexed counters, emitted on the cadence (§8.7).

### 8.1 `southbound_health` — the mandatory shared metric (exactly the eight SOUTHBOUND §5 measures)

Dimensions: `instance`. No extension measures: pause state rides `sb/status`, the keepalive
`PAUSED` token, and the `adapter-paused`/`adapter-resumed` events instead of a gauge.

| Measure | Unit | Res | Meaning |
|---|---|---|---|
| `connectionState` | Count | 1 | 1 = session up (driven with `LinkState`, template `Health::set_link` kept) |
| `signalsSubscribed` | Count | 1 | the configured/served signal inventory the session serves while up (poll: every poll-group signal; push: every declared input+output field — the `sb/signals` set); 0 while disconnected |
| `pollLatencyMs` | Milliseconds | 1 | last poll cycle's read round-trip (whole cycle) |
| `publishLatencyMs` | Milliseconds | 1 | last `data` publish await duration |
| `readErrors` | Count | 60 | signal-read failures over the interval (BAD samples + link-breaking read errors), drained on emit |
| `writeErrors` | Count | 60 | DEVICE-PATH write failures over the interval (the entry passed validation + the allow-list and was then rejected by the device or aborted by an unavailable session; policy refusals / unresolved refs / missing values do NOT count), drained on emit like `readErrors` |
| `staleSignals` | Count | 60 | signals with no GOOD read for > `staleSignalSecs` (0 while paused, §9.3) |
| `reconnects` | Count | 60 | poll-loop exits into reconnect over the interval |

Emitted on the periodic sampler AND immediately (`emit_metric_now`) on connect/disconnect/
pause/resume transitions. This replaces the template's 5-measure ad-hoc set (which omitted
`publishLatencyMs`/`staleSignals` — CLI-DOGFOODING #5); `signalsPublished` moves to
`EtherNetIpPublish` where it belongs.

eviction benign for the thing telemetry cares about: what the adapter publishes is always the
freshest frame, and a consumer that never keeps up is already visible as publish latency and
`sequenceGaps`. Wiring it through the seam is a metric-surface decision on its own evidence, not a
side effect of the queue change.

## 9. State, connectivity & pause reflection

### 9.1 The provider (kept from the template, extended)

ONE `InstanceConnectivityProvider` registered in `App::run`
(`gg.set_instance_connectivity_provider`), one entry per configured device, feeding BOTH the
`state` keepalive's `instances[]` and the built-in `status` verb — push and pull cannot
disagree. Sample shape (verified `InstanceConnectivity` API: `new(instance, connected, detail)
.with_state(token).with_attributes(map)`):

```json
{ "instance": "filler-plc", "connected": true, "state": "PAUSED",
  "detail": "127.0.0.1:44818",
  "attributes": { "adapter": "ethernet-ip", "mode": "poll", "paused": true, "slot": 0,
                  "connectionMode": "unconnected" } }
```

(A push instance reports `"mode": "push"` and `"connectionMode": "class1-io"`; `connected`
means the class-1 connection is open and inside its watchdog window.)

### 9.2 `LinkState` gains `Paused`

```
Connecting ──connect ok──► Online ◄──resume── Paused
     ▲                      │  ▲                │
     └──────backoff◄──break─┘  └────pause───────┘        (break while paused → Backoff,
                                                          reconnect, then back to Paused)
```

Tokens: `CONNECTING` / `ONLINE` / `BACKOFF` / `PAUSED`. The paused flag is stored separately
from the link state (an `AtomicBool` beside `Health`) so a link break while paused reports
`BACKOFF` + `attributes.paused: true`, and re-establishment returns to `PAUSED` (not `ONLINE`).
The reported `state` token is `PAUSED` whenever the instance is paused AND the session is up;
`connected` always tells the truth independently. The template invariant is preserved and
extended: `connected`, `southbound_health.connectionState`, and the state token all derive from
the same `Health` object — and `paused` (attribute, token, `sb/status` field) derives from the
same `AtomicBool` — so no two surfaces can disagree.

### 9.3 Connectivity is driven by real CIP I/O

`Health::set_link` is called only from actual I/O outcomes. Poll: connect result, poll-cycle
result, write result, on-demand read result, and — while paused — the keepalive probe (§7.4.3).
Push: ForwardOpen result, `IoUpdate::Up` (first accepted frame), and `IoUpdate::Lost` (watchdog
timeout / peer close) — the cyclic reception is itself the health signal, paused or not. A
cached socket handle is never consulted. Staleness: per-signal `last_good_read: Instant` (poll:
last GOOD read; push: last accepted frame carrying the field), counted against `staleSignalSecs`
at health-emit time; the clock **suspends during pause** (on resume, `last_good_read` is
re-based so the paused span doesn't count).

## 10. Error handling & reconnect

### 10.1 Classification (`EnipError` → `DeviceError`)

The protocol crate's `EnipError::is_transient()` (PROTOCOL-DESIGN §10.1) is the default; the
backend overrides per this table (which is the adapter's normative behavior):

| Failure | Class | Behavior |
|---|---|---|
| TCP connect refused/unreachable, host-lookup failure, connect timeout (`Io`/`Timeout` on connect) | `Transient` | backoff ladder (a device that is off may come back) |
| Malformed endpoint/config (unparsable host, bad slot, layout/`AssemblyLayout` rejection) | `Permanent` | config-time where possible; else backoff at the ceiling (template rule: never hammer what cannot fix itself) |
| Socket error / session loss / EOF mid-cycle (`ConnectionLost`) | `Transient` | leave engine loop → reconnect |
| ≥ `requestTimeoutMs` timeout on a request (`Timeout`) | first: BAD sample (`"TIMEOUT"`); **3 consecutive** timeouts: the stack itself declares the session lost → `Transient` | isolated slowness ≠ dead link; sustained silence = dead link (the stale-reply quarantine guarantees a late answer can never leak into a newer request — PROTOCOL-DESIGN §10.4) |
| CIP error status for one tag (`Cip`: 0x04/0x05 not-found, 0x08, 0x13, …) | not an error — **BAD Reading** | published; session lives (one dead tag must not blind the other ninety-nine) |
| ForwardOpen rejected (`ForwardOpenRejected`) — class-3 (poll `connected: true`) or class-1 (push) | `Transient` | reconnect ladder; the typed extended status is logged (duplicate connection 0x0100, out of connections 0x0113, bad path 0x0315 …); after 3 consecutive rejections log a mode-specific hint (poll: try `connected: false`; push: check assembly instances/sizes against the device) |
| Class-1 watchdog timeout / peer stops producing (`IoEvent::Lost`) | `Transient` | leave push loop → reconnect (ForwardClose best-effort first); `ioTimeouts` counter + `device-unreachable` alarm |
| Push write refused because the class-1 connection is gone (`Closed` from `stage_output_by`) | `Transient` — an **override** of the crate's non-transient default for `Closed` | inline `ok:false` naming the disposition: the loss's own reason when a `Lost` preceded the removal, otherwise a deliberate close (§7.3, D-EIP-31). The ladder recovers both, so neither may park the instance at the backoff ceiling |
| Push write refused because its own request timeout ran out (unaccepted handoff, unconfirmed verdict, or a command that expired while queued) | `Transient` | inline `ok:false` naming which of the three it was (§7.3, D-EIP-31). Nothing was staged and nothing will be: the deadline rides the command, so an expired one is dropped at the producer buffer rather than applied late |
| Malformed/hostile peer traffic (`Malformed`, `ProtocolViolation`) | `Permanent`-leaning: surface loudly, backoff at ceiling | a peer that breaks the protocol will keep breaking it; per-frame UDP garbage is dropped+counted by the stack without touching the link |
| Browse service unsupported (`Cip` 0x08 on the tag-list service, **start instance 0**) | `Unsupported` | `BROWSE_UNSUPPORTED` reply; never affects the link |
| Browse resume refused (`Cip` 0x08 on the tag-list service, **non-zero start instance**) | `Permanent` | `BROWSE_FAILED` naming the refused instance; never affects the link. The device answered a page already, so the service exists — only the mid-set start is refused (the EthernetIPSharp shape, §11.7), and `BROWSE_UNSUPPORTED` would misreport it as a device that cannot browse at all |
| Browse page out of order or repeating an instance id (`ProtocolViolation` from `list_tags`) | `Permanent` | `BROWSE_FAILED`; the page is refused rather than paged over, because the resume point follows its last record and anything behind that record would be skipped forever (PROTOCOL-DESIGN D-ENIP-19) |

### 10.2 Reconnect

The template's backoff is kept verbatim: exponential from `reconnectBackoffMinMs`, full jitter,
capped at `reconnectBackoffMaxMs`; permanent failures jump to the ceiling. On every
loss: `LinkState::Backoff`, `reconnects`/`connectionDrops` counters, `device-unreachable` alarm
raise; on re-establishment: alarm clear, `device-connected` event, counters — and **pause
survives reconnect** (§9.2). Writes/reads arriving while disconnected fail fast with
`DEVICE_UNAVAILABLE` (the control/write channels are drained with errors during backoff rather
than queueing into a dead link).

### 10.3 Shutdown (D-EIP-27)

Shutdown is **coordinated and deadline-bounded**: `cancel → close → join → flush`.

Every instance runs under a child of one app-wide root `CancellationToken`, and every task it spawns
(the device task, plus the cert-lifecycle task on a TLS poll instance) is registered — with its
`JoinHandle` — in the live `DeviceRegistry` (`lifecycle.rs`). On `gg.shutdown_signal()`:

1. **Cancel the root.** Every instance's child token fires at once, so the whole fleet tears down
   concurrently rather than one instance's budget after another's.
2. **Each task closes its own session on the way out.** The session is `!Sync` and owned by the
   device task (the same reason the `DeviceControl` channel exists), so nothing outside it can close
   it. The poll driver closes on cancel and returns `PollExit::Stopped` — `EipClient::close()` sends
   UnRegisterSession (and the class-3 ForwardClose when connected). The push driver returns
   `PushExit::Stopped` and the unconditional `session.close()` that follows it ends the class-1
   session. A cancel arriving mid-backoff leaves `serve_control_disconnected`
   immediately with `DisconnectedWait::Stopped`; a cancel arriving mid-connect drops the connect
   future (no session exists yet). **None of these paths raises `device-unreachable`, emits an event,
   or backs off** — the link did not fail, the instance was stopped.

   **The push close is a handoff that always ends the translator (D-EIP-31).** The class-1 client,
   I/O manager and connection handle live in the translator task, so `close()` hands it
   `PushControl::Close`, waits for its acknowledgement under the 5 s `PUSH_CLOSE_HANDOFF_CAP` — one
   absolute deadline over both the handoff and the ack — and, if either outlives that cap, **aborts
   the translator and joins it** (a fixed 250 ms `ABORT_JOIN_GRACE`, which is scheduler slack over a
   causal wait, not a race). Either way, `close()` returning *means* the translator has ended. An
   aborted one skips the courtesy ForwardClose / `IoManager::shutdown` / `EipClient::close`;
   teardown still completes through the Drop chains (the manager's command channel closes, its task
   exits and drops the UDP socket; the client's actor channel closes, the actor exits and drops the
   TCP stream) and the target times its class-1 connection out on its own watchdog rather than being
   told. That is the same trade `stop_tasks`' abort already makes at the budget. A session dropped
   **without** `close` — an outer device task aborted at the budget, a panic unwinding past it — gets
   the same guarantee from `EipPushSession`'s `Drop` abort, and therefore the same trade: the
   courtesy frames are for the paths that stayed inside their budget.
3. **Join under ONE absolute budget, then abort stragglers.** `stop_budget(timeouts)` composes
   the Phase-1 per-session bounds: one in-flight-request bound (a cancel arriving during a CIP
   read/write is observed only after that call resolves — bounded by `requestTimeoutMs`) + the worst
   per-session close bound (`max(` push close-handoff cap 5 s`,` `requestTimeoutMs` + the 2 s `enip`
   session-close handoff`)`) + 500 ms grace, clamped to **[1 s, 10 s]** so a pathological
   `requestTimeoutMs` cannot make shutdown outlive a supervisor's grace period (Kubernetes default
   30 s, Greengrass default 15 s). At the shipped defaults that is 2 s + 5 s + 0.5 s = **7.5 s**. A
   push close that overruns its cap spends a further 250 ms joining the translator it aborted, so its
   true worst case is 5.25 s; that overshoot is **absorbed by the 500 ms grace** — which exists for
   exactly this kind of per-session slack — rather than added to the composition, and the shipped
   number stays 7.5 s. The deadline is absolute across the whole fleet, not per task; whatever is
   still running when it expires is `abort()`ed and counted, so a wedged peer can never hang the
   process. The teardown logs `joined`/`aborted`/`budget_ms`.
4. **`flush_metrics()` last**, so the final counters ride out while messaging is still up. The
   library's RAII then handles unsubscribes and the `STOPPED` state when the runtime drops (the org
   unsubscribe-before-exit rule is satisfied by RAII).

The drain is a loop, not a single pass: a runtime inserted after the root was cancelled gets a child
token that is *born cancelled*, so it exits immediately and is reaped by the next pass. Everything is
idempotent — `cancel()` is idempotent, `close()` is idempotent per the seam contract, and the drain
consumes — so a second pass over an empty registry is a no-op.

**A failed startup takes the same path.** `App::run` launches instances one at a time and is still
fallible after the first of them is polling (minting an instance facade, registering the command
surface), so the whole setup runs behind `lifecycle::stop_on_startup_error`: an `Err` cancels the
root and drains the registry under the same `stop_budget` before it propagates. Without that, an
adapter that failed to start instance *N* would exit leaving instances *1…N-1* publishing, their
sessions never unregistered and their class-1 connections never ForwardClosed.

Consequence, stated plainly: in-memory pause state (D-EIP-14) dies with the task it lived in.

### 10.4 Configuration reload (D-EIP-28)

A configuration change applies as **one transaction over the live instance set**. The adapter
registers exactly one `ConfigurationApplyListener` — `reload::ReloadCoordinator` — at startup, and
core drives it for every reload source (the `-c FILE` watcher, a Kubernetes ConfigMap update,
`GG_CONFIG`, the built-in `reload-config` verb), serialized by core's apply lock.

**The core contract, and what it obliges us to do**

| Core stage | Our obligation |
|---|---|
| `prepare_configuration_apply(candidate)`, under `tokio::time::timeout(validationTimeout ≈ 5 s)`, must not change the live runtime | Ours is **allocation-only**: parse `component.global`, diff the candidate against the running set, stage the transaction. No sockets, no broker, no spawns, no registry mutation. |
| `commit()` is awaited with **no** external timeout, while the OLD snapshot is still `gg.config()` | Every stage bounds itself, and commit waits on exactly two kinds of thing. The stop stage runs under §10.3's `stop_budget` and aborts stragglers, so a wedged device cannot hang a reload. The two operator notifications — the removed instances' alarm clear and `config-applied` — go out through a plain publish, which awaits a funnel send and a submission ack with **no timeout of its own**; each is therefore wrapped in a short best-effort budget (`reload::NOTIFY_BUDGET`, 2 s), logged and skipped on expiry, so a wedged broker or a saturated funnel cannot stall a commit while it holds core's apply lock and queues every later reload behind it. A failed notification never fails a reload. |
| Core stores the candidate and bumps the generation only **after** commit returns `Ok` | Instances launched during commit are bound to the candidate snapshot explicitly (`instance_from_config_snapshot`), not to whatever core currently publishes. |
| On a commit `Err`, core awaits `rollback()` fully, then keeps the prior snapshot | `rollback` stops what the commit launched and relaunches the instances it stopped, bound to the **prior** snapshot and global. |

**Granularity: instance-diff restart.** The plan (`reload::plan`, pure) compares the candidate's
`component.instances[]` entries against the **running set** — the registry's `(id, raw)` snapshot,
deliberately not the previous `Config`, so an instance that was skipped at startup starts now even
though its subtree never changed. Comparison is `serde_json` structural equality, so a re-serialized
document with reordered keys is not a change.

- unchanged instance → **kept**: same task, same session, same facades, same `Arc<GlobalConfig>`, same
  `Health` — and therefore the same pause state;
- new instance → **started**; instance no longer declared → **stopped**;
- changed instance → **stopped, then started**;
- **any change outside `component.instances`** → every instance restarts (see D-EIP-28 for why).

**Commit, in order.** (1) Refuse if the shutdown root is already cancelled. (2) Remove the instances
being replaced from the registry *first*, so command routing answers `NO_SUCH_INSTANCE` /
`DEVICE_UNAVAILABLE` during the swap instead of dispatching into dying channels; capture the event
sink of every instance with no successor, because the stop consumes the runtimes. (3) Stop them with
§10.3's engine, so a replaced device's session is UnRegisterSession'd / ForwardClose'd before its
successor connects; a budget overrun aborts stragglers and is *not* a commit failure. (4) **Then**
clear the `device-unreachable` alarm of every instance with no successor — nothing would ever clear it
again (a restarted instance clears its own on the next connect). Clearing *before* the stop would race
the instance's own alarm: a link drop in that window — which spans a broker round-trip per earlier
removal — re-raises the alarm behind the clear, and it latches on the bus forever. (5) Publish the
candidate's global. (6) Launch the added/changed instances through `RuntimeLauncher::launch`, applying
**the same two-class rule startup applies** (`launch_startup_set`), because it is one rule and not two:
a refusal whose cause is an `adapter` token no backend implements is a **bad instance** — skipped with
a warning **and reported in the event's `skipped` list**, so no id vanishes from the record; **any
other construction failure is a broken runtime and fails the commit** on the spot (`LAUNCH_FAILED`,
naming the instance), whereupon core's fully-awaited `rollback` stops whatever this commit had already
launched and relaunches the stopped instances against the prior snapshot and global. An all-skip launch
pass that keeps nothing still fails with `NO_RUNNING_INSTANCES` — the only shape that now reaches it.
(7) Recompute the `repoll` availability and emit `config-applied` (`started`/`stopped`/`kept`/
`skipped`/`restartAll`). (8) Record the new generation as the one the next reload diffs against —
without which every later candidate would re-diff against the startup document and restart the fleet.

Stage 7 is unreached on the `LAUNCH_FAILED` path, so a failed commit leaves no success surface behind:
no `config-applied`, no recomputed availability, no advanced generation. Core carries the code outward
in its own `RELOAD_FAILED` / `lastErrors`. Stage (4) has by then already cleared the
`device-unreachable` alarm of the instances the candidate removed; rollback relaunches them and a
genuinely unreachable device re-raises its own alarm on the next connect attempt, so the clear is
transient rather than a lost alarm. Deferring the clear until after the launch stage is *not* the fix —
it would reopen exactly the latch-forever race stage (4)'s ordering exists to prevent.

**Invalid candidates.** A malformed instance is skipped with a warning, exactly as at startup, and so
is one whose `adapter` token no backend implements. A malformed `component.global`, or a candidate with
**no valid instance at all**, is rejected at prepare (`INVALID_GLOBAL` / `NO_VALID_INSTANCES` in core's
`lastErrors`) and the running generation keeps operating — the reload-time analog of startup's
refuse-to-start, where there is nothing running to keep. A candidate that passes prepare but cannot be
brought up is rejected at commit instead (`LAUNCH_FAILED`, or `NO_RUNNING_INSTANCES` when every start
was skipped and nothing was kept), and rollback puts the previous generation back.

**Verbs and surfaces do not re-register.** All nine `sb/*` verbs stay registered once at
`CommandScope::Instance`; the `Commander` reads the registry per request, so a removed instance
answers `NO_SUCH_INSTANCE` and an added one is routable the moment commit inserts it. The
connectivity provider likewise reads the registry, so a keepalive tick mid-commit publishes the
mid-swap truth. Metric families are re-defined per launched instance (`define_metric` replaces by
name, so it is idempotent) and nothing is undefined for a removed instance — families are shared and
`instance` is a dimension, so a removed instance simply stops emitting. Metric **target** changes are
core's own post-commit business, not the adapter's.

**Both directions of the reload/shutdown race are closed.** Prepare and commit both refuse once the
root token is cancelled (`SHUTTING_DOWN`), and §10.3's drain loop reaps anything a commit inserted
just before the cancel, because its child token is born cancelled. A reload arriving before the
startup launch loop has published its surfaces is refused with `STARTING`.

**Rollback fidelity, stated honestly.** Rollback restores the prior generation's *set and
configuration*, not its live state: restored instances reconnect with fresh sessions, in-memory pause
on a restarted or stopped instance is gone, and interval counters restart. What can never be lost is
the prior configuration itself — core keeps the snapshot, and the transaction retained every stopped
instance's parsed config plus its raw subtree. Registry order after a reload is kept-instances first,
then newly-launched ones, which affects only the cosmetic ordering of the connectivity list (the
single-instance command default depends on the *count*, not the order).

**Consequence, documented rather than hidden:** pause is in-memory (D-EIP-14), so an instance that
restarts as part of a reload resumes publishing. Pause survives only on instances the reload did not
touch.

**CIP Security Phase-2a validation.** The OpENer `CIPSecurity` branch implements the three security
objects (0x5D/0x5E/0x5F) as real CIP objects — but stubs the TLS transport — so it serves genuine
`Get_Attribute_Single` reads of the posture over the plaintext explicit session
(`test-infra/opener-cipsecurity/`, `:44822`). `crates/enip/tests/live_cip_security.rs` (self-skipping on
a `:44822` probe) drives the real `enip::read_security_posture` against it and asserts the typed decode
against an independent implementation: CIP Security state (`Factory Default`), the EtherNet/IP
Confidentiality **profile** bitmap, the count-prefixed **cipher-suite lists**, the verify-client /
check-expiration flags, and the Certificate Management summary (push capability, cert instance name
`"Default Device Certificate"` / state `Verified` / encoding `PEM`) — all decoded correctly. The branch
is stalled (Dec 2023) and its Certificate Management object depends on the separate OpENerFileObject
project; the Dockerfile carries the vendoring/link/init patches to stand it up (never patching `enip`),
per the ab_server precedent. Real-device posture semantics (a commissioned Vol 8 PLC's populated suite
lists / `Configured` state) remain the declared lab-hardware gap (§14.6).

**CIP Security Phase-2b validation (managed trust store + cert rotation).** The pure lifecycle logic —
managed trust-store building from multiple/multi-version CAs, the client-cert expiry parse + threshold,
the rotation-detection fingerprint, and the connect-time refuse-on-expired — is unit-tested in
`eip/tls.rs` + `eip/rotation.rs`. The **rotation is proven end-to-end over the same stunnel/cpppo TLS
peer** by two self-skipping (`:2221` probe) tests in `eip/tls.rs`: `live_client_cert_rotation_…`
connects over TLS with the originator cert, rotates the vault to a fresh cert (signed by the same CA —
the `ec-secrets` shape), confirms the lifecycle watcher reports the rotation, and asserts the next
`connect_tls` presents the **new serial** (accepted by the `verify=2` peer); `live_near_expiry_cert_…`
proves a ~20-day cert fires `cert-expiring` at the 30-day threshold. Certified-Vol-8-device rotation
semantics remain the declared lab-hardware gap (§14.6).

**EST enrollment (Phase 2c, D-EIP-24).** The owned RFC 7030 client is unit-tested end-to-end: the pure
pieces (config parse/validate + destination derivation, URL parsing, CSR generation, HTTP request
encoding + response parsing, the renew-window scheduler, the vault write-back) plus a **golden PKCS#7
vector produced by OpenSSL** (`crl2pkcs7`) prove the parser against an independent encoder; and an
**in-process rustls EST responder** drives the full `enroll_once` path — real TLS handshake, HTTP,
base64, PKCS#7 parse — asserting the issued cert lands in the vault and Phase 2b's watcher reports the
`Rotated` handoff. Live: `test-infra/est/` runs the independent Go **globalsign/est `estserver`** (+ mock
CA) over mutual TLS on `:8443`, and the self-skipping `live_est_enroll_…` test (inline in `eip::est`,
probing `:8443`) enrolls a real originator certificate against it. Enrollment against a real CIP Security
**device**'s pull-model PKI remains the declared lab-hardware gap (§14.6).

**Browse-gap status: CLOSED (sim-grade).** The tag-list service (Get Instance Attribute List `0x55`
on the Symbol class `0x6B`) — which cpppo and ab_server both refuse — is served by EthernetIPSharp,
so `enip::list_tags` now has a genuine on-the-wire validation against an independent implementation
(§11.7). The **real-Logix** browse path (a physical controller, multi-page enumeration of hundreds of
tags, `RECIPE`/UDT `supported:false` semantics on real Rockwell symbol types) remains a lab-hardware
path (§12.4) — sim-grade `0x55` conformance is not plant-grade.

### 11.1 The cpppo simulator (POLL) — tag layout (the sim contract)

Image `cpppo/cpppo`, running the Allen-Bradley ControlLogix tag server on TCP **44818**. The
canonical tag set (bottling-line flavored, matching §4.5 and the de-risk probe):

```bash
python -m cpppo.server.enip --address 0.0.0.0:44818 -v \
  LINE_SPEED=REAL FILL_TEMP=REAL TANK_LEVEL=REAL PRODUCT_COUNT=DINT \
  FILL_SETPOINT=REAL ZONE_TEMPS=REAL[8] MOTOR_RUN=DINT RECIPE=SSTRING
```

| Tag | Type | Role in validation |
|---|---|---|
| `LINE_SPEED`, `FILL_TEMP`, `TANK_LEVEL` | REAL | fast-group scalars; deadband + scale/offset paths |
| `PRODUCT_COUNT` | DINT | integer decode path |
| `ZONE_TEMPS` | REAL[8] | **array** read → JSON array of 8; array write shape |
| `FILL_SETPOINT` | REAL | **writable** setpoint (in `writes.allow[]`) — confirmed write + poll-observed readback |
| `MOTOR_RUN` | DINT (0/1) | writable command-style value (cpppo models BOOL awkwardly; DINT stands in — a real Logix BOOL uses `type: bool`) |
| `RECIPE` | SSTRING | deliberately UNSUPPORTED type: proves config validation rejects `string` (the `sb/browse`-marks-it-unsupported check is a real-Logix path — see the browse note below) |

cpppo has no backplane ⇒ config omits `slot` (`PortSegment::default()`); the `slot` path is a
lab-PLC concern (§12.4).

**Live finding (S7) — tag-list browse is NOT servable by cpppo.** cpppo 3.9.7's `enip.server` does
not implement the Logix tag-enumeration service (Get Instance Attribute List, `0x55` on the Symbol
class `0x6B`): its request parser rejects the service at byte 0 and drops the TCP session (server
status `0x08`). The request `enip` emits is the standard form a real Logix controller answers, so
this is a cpppo capability gap, not an `enip` bug — and OpENer (a generic adapter with no Logix
Symbol object) cannot serve it either. What the live suite proves against cpppo is that `enip` emits
the well-formed request and surfaces the device's refusal as a *typed* error (the adapter's
`BROWSE_UNSUPPORTED`), never a panic — the exact generic-CIP-device path
(`crates/enip/tests/live_cpppo.rs::cpppo_live_tag_browse_is_gracefully_refused`). **The positive
browse path — a real `0x55` reply decoded by `enip::list_tags` — is now served by EthernetIPSharp
(§11.7); `RECIPE`/UDT `supported:false` semantics on real Rockwell symbol types stay a real-Logix
(lab, §12.4) path.**

### 11.2 compose.yaml — the sim services, and how each consumer reaches them

The HOST pack (emqx + adapter) sits alongside the peers. The poll sim:

```yaml
  enip-sim:
    image: cpppo/cpppo:latest
    container_name: ethernet-ip-adapter-enip-sim
    command: >
      python -m cpppo.server.enip --address 0.0.0.0:44818 -v
      LINE_SPEED=REAL FILL_TEMP=REAL TANK_LEVEL=REAL PRODUCT_COUNT=DINT
      FILL_SETPOINT=REAL ZONE_TEMPS=REAL[8] MOTOR_RUN=DINT RECIPE=SSTRING
    restart: unless-stopped
```

and the class-1 push target (§11.5), which carries the `opener-sim` network alias the push
test-configs resolve:

```yaml
  enip-io-sim:
    build: ./test-infra/opener      # small owned Dockerfile over EIPStackGroup/OpENer (§11.5)
    container_name: ethernet-ip-adapter-enip-io-sim
    command: ["eth0"]
    networks: { default: { aliases: [opener-sim] } }
    restart: unless-stopped
```

**Neither of those two publishes a host port**, deliberately: the containerized E2E (§11.4) reaches
them by service name on the compose network, where a publish buys nothing. The peers that exist only
to serve a host-side test do publish — `enip-ab-server` `44820:44818`, `enip-sharp` `44821:44818`,
`enip-tls` `2221`, `enip-tls-cbc` `2223`, `opener-cipsec` `44822:44818`, `est-server` `8443`.

So the two unpublished services need something extra whenever a **host-side** consumer dials them,
and the live suites are exactly that: `live_cpppo` hard-codes `127.0.0.1:44818` (a const, not an env
override) and `live_opener` defaults to `127.0.0.1:44819`.

- **CI** layers `test-infra/ci-overrides.yaml` over the base file. It *adds* a cpppo publish (there
  is no `ports:` key to override) and scopes it to **`127.0.0.1` only** — which is not a detail but
  the whole answer to a bind conflict: a wildcard `44818:44818` makes docker-proxy listen on
  `0.0.0.0:44818` and blocks every later bind of that port, so the host-networked OpENer the class-1
  legs require would die on `EADDRINUSE`. Loopback-scoping leaves the runner's primary IPv4 free for
  it. `enip-io-sim` is built but never started from compose there; the job runs the same image with
  `--network host` (§11.3).
- **A bench** wanting the host-side suites can layer the same overlay for cpppo. OpENer must run
  natively or `--network host` on a Linux docker host: a bridge-NATed OpENer cannot serve class-1 at
  all, because the T→O UDP return path does not survive the NAT (and on Docker Desktop for Windows
  the WSL2 NAT breaks it regardless — §11.3).

Adapter configs point at `enip-sim:44818` / `opener-sim:44818` on the compose network, and at
`127.0.0.1:44818` / `127.0.0.1:44819` in `test-configs/` for a bare `cargo run` against
`docker run`-started sims. cpppo tags and OpENer assemblies reset on container restart — E2E writes
must not assume persistence. **Class-1 note:** the adapter binds an **ephemeral** UDP source port per
push session and advertises it in the ForwardOpen's Sockaddr Info items, so it never contends with
OpENer for the target's `:2222`; compose must still run the adapter and `opener-sim` on the same
network, because the T→O return path goes to that advertised address and must not cross a NAT.

### 11.3 Sim-gated integration tests (six suites)

Six live-peer suites in `crates/enip/tests/`, plus three **in-source** live tests in the adapter
crate. All of them self-skip: a `TcpStream::connect` probe with a short timeout at suite start; on
failure every test returns early with an eprintln "skipped (no …)" — exactly the sibling pattern
(Modbus's live-slave gating). Each has its own default port (overridable by env var) so it fires
only when its own peer is up, which is what keeps `cargo test --workspace` green on a bench with no
containers.

**`ENIP_LIVE_REQUIRED=1` turns the skip into a failure.** Under it a probe that finds no peer
panics instead of printing a skip, so a live run cannot pass vacuously. Each suite carries its own
six-line `live_required()` helper — `ENIP_LIVE_REQUIRED` set, non-empty, and not `0` — matching the
per-suite `sim_up()` convention rather than introducing a shared `tests/common` module (which would
change the §12.2 coverage regex). There are **21 hardened skip sites across 8 files**, of two kinds
whose rationales differ:

- **20 reachability sites** — a peer that does not answer its probe, or live test material that is
  not on disk. 14 sit in the six suites (`live_cpppo` 3, `live_opener` 3, `live_ab_server` 2,
  `live_ethernetipsharp` 3, `live_tls` 2 — the `:2221` probe and the CBC `:2223` probe —
  `live_cip_security` 1) and 6 in the three in-source live tests, where the generated test PKI is
  gated too: a missing cert file is its own skip site.
- **1 harness-configuration site** — `live_opener`'s watchdog leg needs a shell command that
  silences the target (`OPENER_STOP_CMD`), and an unset or empty one retires the assertion while the
  job still reports success. That is precisely the vacuous pass this variable exists to eliminate, so
  required mode fails on it as well.

The split is the rule, not bookkeeping: required mode punishes a peer that was not **reached** or a
harness that was not **configured**, and never a peer that legitimately refuses a service it does not
implement (the soft paths below). Every assertion message names the peer, its address, and the
command that starts it. With the variable unset the bench behaviour is unchanged.

**What that is protecting against, concretely.** Standing this gate up found that the EST live leg
had never been runnable: `test-infra/est/gen-certs.sh` was broken three ways on Linux — it did not
`mkdir -p` the gitignored `certs/` directory, it wrote subjects in the Windows `//CN=` idiom that a
Linux OpenSSL reads literally and turns into an *empty* subject, and it omitted an `-extfile`, so
`openssl x509 -req` minted an X.509 **v1** client certificate that rustls rejects outright. Any one
of those makes `live_est_enroll_against_globalsign_estserver` impossible to pass. None of them was
visible, because `certs/` does not exist in a clean tree, so the test always took the certs-missing
skip and reported green. That is the same defect class as the coverage carve-out this phase removed:
cited evidence that never actually ran. Gating the material as well as the peer is what turns it into
a failure someone has to look at.

Covered live paths:

- **`live_cpppo.rs`** (poll, `:44818`): connect; scalar/array/DINT reads with exact seeded values;
  write + readback of `FILL_SETPOINT`; per-tag BAD on a nonexistent tag while others stay GOOD;
  that browse (`0x55`) is *typed-refused* — cpppo does not implement the tag-list service (§11.1), so
  the client surfaces the refusal as a typed error, never a panic; and the class-3 inactivity
  keepalive across a 75 s idle (PROTOCOL-DESIGN §7.6) — the second peer for that leg, so it stands as
  long as either peer serves a class-3 connection (this one does not; see the soft paths below).
- **`live_opener.rs`** (push, `:44819`): ForwardOpen against the OpENer sample assemblies (§11.5);
  cyclic consume ≥ N frames with an advancing class-1 sequence; O→T produce observed via OpENer's
  sample output→input **mirror** (`AfterAssemblyDataReceived` copies the consumed output assembly into
  the produced input assembly, so a value we produce reappears in the next consumed frame); watchdog
  `IoEvent::Lost { Timeout }` when the target is silenced; the class-3 inactivity keepalive across a
  75 s idle on defaults (2 s RPI × ×16 ⇒ a 32 s window, probes every 24 s — PROTOCOL-DESIGN §7.6);
  and latest-wins overflow (PROTOCOL-DESIGN §8.6) under a 10 ms-RPI flood the consumer ignores for
  10 s, where the first sample it then reads sits past the evicted prefix instead of at the start of
  the run.
- **`live_ab_server.rs`** (poll, `:44820`, §11.6): the same read/write surface as cpppo but reached
  through a real Unconnected_Send (`0x52`) **route wrapper** (`ClientOptions.route =
  RoutePath::backplane_slot(0)`) — the backplane path cpppo never exercises; browse is typed-refused
  (`0x08` — ab_server has no `0x55` service).
- **`live_ethernetipsharp.rs`** (poll + browse, `:44821`, §11.7): read/write cross-check against a
  third independent implementation, plus the **browse gap-closer** — a real `0x55`
  Get-Instance-Attribute-List reply paged to completion and decoded by `enip::list_tags`, asserting
  the enumerated tags' symbol types (scalars value-supported, the REAL[8] array value-unsupported);
  and the **browse-cursor leg** — the exactly-once ascending walk, plus a >`0xFFFF` cursor emitting
  the 32-bit instance segment (`0x26`) that this independent decoder parses and answers at the CIP
  layer.
- **`live_tls.rs`** (poll over **TLS**, `:2221`; needs `--features tls`): CIP Security Phase 1
  against the OpenSSL `stunnel` terminator fronting cpppo — mutual-TLS connect plus tag read/write
  over TLS, and the negative matrix: wrong CA ⇒ `PeerUnverified`, missing client cert rejected by
  the peer's `verify=2`, and a deliberately CBC-only terminator on `:2223` proving the typed
  `NoCipherOverlap` (DESIGN-cip-security.md §5.2).
- **`live_cip_security.rs`** (posture reads, `:44822`): CIP Security Phase 2a against the OpENer
  `CIPSecurity` branch — real `Get_Attribute_Single` reads of 0x5D/0x5E/0x5F decoded by
  `enip::read_security_posture` into the CIP Security state/profiles, the EtherNet/IP Security
  cipher-suite lists and flags, and the Certificate Management summary (DESIGN-cip-security.md
  §4.1).

The three **in-source** live tests follow the same pattern from inside the adapter crate:
`eip/tls.rs`'s `live_client_cert_rotation_presents_the_new_cert` and
`live_near_expiry_cert_fires_expiring` (both probing the `:2221` stunnel terminator) and
`eip/est/tests.rs`'s `live_est_enroll_against_globalsign_estserver` (probing the `:8443`
globalsign/est server).

The six suite **files** sit outside the coverage denominator (§12.2), because test code that only
executes against a live peer says nothing about product-code coverage — what they are is conformance
evidence against independent implementations. **No product file is excluded.** The three in-source
live tests are *inside* the denominator and simply read uncovered on a bench with those containers
down. *(The protocol crate's own `duplex`-fixture state-machine tests — PROTOCOL-DESIGN §12.2 — need
no container, are NOT gated, and run everywhere.)*

**What stays soft on purpose.** Required mode enforces that a peer was **reached**; it never demands
that a peer implement a service it does not have. These in-body paths therefore stay soft even under
`ENIP_LIVE_REQUIRED=1`, each because of a measured peer limit:

- **cpppo refuses class-3.** Its ForwardOpen to the Message Router is rejected, so the class-3
  idle-survival leg cannot run against it and prints a bench gap rather than faking a result. The leg
  stands on OpENer, which does accept class-3 — but OpENer does not itself enforce the inactivity
  watchdog, so what it proves is the test's stated two-level claim: the keepalive probes are
  well-formed, an independent implementation decodes and answers them, they fire on the ¾-window
  cadence, and the session is still usable after a multi-window idle. Target-*enforced* survival
  needs a peer that enforces the timeout, and stays on the §14.6 real-Logix row.
- **EthernetIPSharp serves `0x55` only from start instance 0.** It has no resume capability, so a
  mid-set cursor is answered with a typed CIP refusal and a multi-page walk is unobtainable at any
  page size. The test records that as the peer's capability and asserts the refusal's shape;
  multi-page paging and mid-set resume stay on the §14.6 lab row.
- **cpppo and ab_server have no `0x55` at all**, so their browse legs assert the *typed refusal* — a
  real pass, not a skip.
- **The latest-wins flood leg needs a peer that accepts a 10 ms RPI.** A refusal is recorded as a
  bench gap rather than asserted. (The watchdog leg's `OPENER_STOP_CMD` is deliberately *not* in this
  list: that is harness configuration, and required mode hardens it — see above.)

**The gate: the `live-sims` job.** `.github/workflows/ci.yml` runs every suite above against real
peers on `ubuntu-latest` **on every pull request**, with `ENIP_LIVE_REQUIRED=1` on each test step, so
a peer that failed to start turns the job red instead of green-with-skips. The TCP peers come up from
`compose.yaml` with `test-infra/ci-overrides.yaml` layered on top (`enip-sim`, `enip-ab-server`,
`enip-sharp`, `enip-tls`, `enip-tls-cbc`, `opener-cipsec`, `est-server`); OpENer runs separately as a
**host-networked** container (`opener-live`) because the class-1 T→O return path cannot cross a
bridge NAT. Those two placements are one decision: the overlay publishes cpppo on **127.0.0.1 only**,
which leaves the runner's primary IPv4 `:44818` free for OpENer to bind — a wildcard `44818:44818`
publish would claim that port and OpENer would die on `EADDRINUSE` (§11.2).
`test-infra/wait-ports.sh` then gates the suites on a real `accept()` from all eight addresses (a
60 s budget each, and a failure names the peers that never came up) rather than on a sleep, and both
throwaway PKIs are generated before the images are built.

Execution is split across four steps, all of it forced by the single-threaded OpENer sample: the TCP
suites first; then the adapter's in-source live tests, matched by name so a new `live_…` test joins
the gate by existing; then `live_opener`'s class-3 idle and latest-wins flood legs with
`--test-threads=1`, because run in parallel a class-1 timeout closes the TCP session the class-3 leg
is idling on and one root cause reports as two failures; and **last, on its own**, the watchdog leg
with `OPENER_STOP_CMD=docker kill opener-live` — that leg leaves the peer dead, and alphabetically it
would otherwise run first and sabotage the other two.

**Bench versus Linux runner.** The TCP peers are reachable from any dev bench. The **class-1 UDP legs
are not**: on Docker Desktop for Windows the WSL2 UDP NAT breaks the T→O return path, so
`live_opener`'s ForwardOpen/consume/produce/watchdog and latest-wins legs need a Linux docker host
with OpENer on host networking (or OpENer built natively). So a Windows developer can reproduce every
TCP suite locally but not the class-1 ones, while the `live-sims` job proves all of them on each PR.
That asymmetry is a property of the bench, not of the code — worth knowing before reading a local
"skipped (no OpENer)" as agreement with CI.

**Live findings (S7) — two `enip` interop fixes surfaced by OpENer (the first real class-1 target).**

1. **ForwardOpen must advertise the originator's I/O receive endpoint.** `IoManager::forward_open`
   now appends the O→T (`0x8000`) and T→O (`0x8001`) **Sockaddr Info items** to the ForwardOpen CPF,
   carrying the scanner's actual UDP receive port. A target defaults its T→O destination to the
   standard implicit-I/O port `2222`; OpENer takes it from the T→O item's `sin_port` instead. This
   both matches real-originator behavior and lets the scanner bind an ephemeral port rather than
   fight the target for `:2222` when scanner and target share a host (`cm_ucmm` gained an
   `extra_items` parameter; `forward_open` fills it, `close` passes none). OpENer validates incoming
   O→T by source *IP only* (not port), so the scanner's single ephemeral socket serves both
   directions.
2. **The CM/UCMM reply decode tolerates trailing bytes.** OpENer echoes the Sockaddr Info items back
   on a ForwardOpen *reply* and, on its reject path, leaves the CPF `item_count` at 2 while still
   appending them. The reply decode now honors the declared item count and ignores trailing bytes
   (`Cpf::decode_from` in `client/io_service.rs`) instead of asserting end-of-buffer, so a real
   target's reply is never rejected as malformed. (The strict end-of-buffer `Cpf::decode` is retained
   for the explicit-messaging reply paths.)

Both fixes are covered by the `enip` unit suite (re-run green) and proven end-to-end against real
OpENer; the class-1 UDP loop requires host/native networking on Linux (the Docker-Desktop-Windows
WSL2 UDP NAT breaks the T→O return path — §11.2).

### 11.4 E2E validation plan (HOST, scripted; the "does it really work" pass)

Stack: EMQX (`localhost:1883`) + cpppo + OpENer + the adapter (`--platform HOST --transport
MQTT`), configured with BOTH instances: `filler-plc` (poll, §4.5) and `palletizer-io` (push,
§4.6). Ordered checks, each observed on the bus (MQTTX/mosquitto_sub over the §6.1 topics) or
via request/reply:

1. **Poll → data**: `ecv1/+/ethernet-ip-adapter/filler-plc/data/#` carries
   `SouthboundSignalUpdate` for the fast group at ~500 ms; `zone-temps` value is a JSON array
   of 8; identity element stamped; quality GOOD with `qualityRaw: "0x00"`.
2. **Push → data**: `ecv1/+/ethernet-ip-adapter/palletizer-io/data/#` carries updates sourced
   from cyclic frames (respecting `sampleMs`/deadband, NOT one publish per 100 ms frame);
   `signal.id`s are the `a100/…` forms; `serverTs` tracks frame arrival.
3. **State**: keepalive `instances[]` shows both instances `connected: true` (`ONLINE`), the
   push one with `connectionMode: "class1-io"`.
4. **sb/read**: poll — by name and explicit ref, values matching a parallel cpppo client read;
   push — snapshot values with the frame-arrival `serverTs`.
5. **sb/write**: poll — `FILL_SETPOINT` → 55.5 confirmed `ok:true`, next poll publishes 55.5,
   `write-audit` event observed; non-allow-listed refusal + Warning audit + `writeFailures`
   increment. Push — `dout-word` write `ok:true` with `applied: "next-frame"`, and the O→T
   frame observably changes; a write to an input field refused inline.
6. **sb/pause / sb/resume (both modes)**: pause each instance → its `data` traffic stops; state
   token `PAUSED`; `sb/status` `paused: true`; `adapter-paused` event; `sb/read` still
   answers; **push: `framesConsumed`/`framesProduced` keep counting while paused** (the
   connection lives, D-EIP-20); resume → traffic returns, the surfaces flip back, no
   burst of stale "changes" (§7.4.8).
7. **Metrics**: with `metricEmission.target: messaging`, the `metric` class shows all seven
   families (§8.1–§8.8) with the §8 measure names; Total counters monotonic, Interval counters
   reset; `EtherNetIpIo.interFrameMs` ≈ the negotiated API.
8. **Failure — poll**: stop cpppo → `device-unreachable` alarm raise, `connectionState` 0,
   BACKOFF state; restart → clear + recovery.
9. **Failure — push**: `docker pause` opener-sim → within `timeoutMultiplier × API` the
   watchdog fires: `IoEvent::Lost`, alarm raise, `ioTimeouts` increments, BACKOFF; `docker
   unpause` → ForwardOpen re-establishes, alarm clears, frames resume.
10. **Browse**: `sb/browse` on `filler-plc` lists the 8 tags, `RECIPE` `supported: false`,
    `configured` flags correct.

### 11.5 The class-1 push target — OpENer (external container)

**Recommendation: OpENer** (`EIPStackGroup/OpENer`, the ODVA-member OSS EtherNet/IP
*adapter/target* stack) as the live push target: it is an independent implementation (a genuine
conformance check, not our own code talking to itself), implements class-1 produced/consumed
assemblies with the standard demo application. **Confirmed live (S7)** from the OpENer sample
(`sample_application/sampleapplication.c`): input (T→O) **100** / output (O→T) **150** / config
**151**, sizes **32 / 32 / 10** bytes, exclusive-owner (`150→100→151`) — exactly the §4.6 /
`test-configs/config-opener.json` layout, so no config fork was needed. It builds trivially on
Linux (`test-infra/opener/Dockerfile`; the only non-obvious dep is `libcap`). **Flag: there is no widely-published official OpENer container image** — the repo ships
source + CMake, so `test-infra/opener/Dockerfile` (a ~15-line build stage over the sample app)
is part of this design, not an off-the-shelf pull.

**No in-crate CI fallback.** There is no embedded push target (user decision — all device
simulators are external containers). Push integration tests gate on the external OpENer container
and self-skip on a port probe if it is absent (§11.3), exactly like the cpppo poll tests. The
protocol crate's *own* session/connection logic is proven without any container via in-memory
`tokio::io::duplex` byte-stream fixtures (PROTOCOL-DESIGN §12.2/§12.5, D-ENIP-14); those fixtures
inject crafted/stale/fragmented bytes a real target can't be scripted to send, but they are not a
conformance peer — real-device push conformance comes only from OpENer. If OpENer is unavailable
for a release, that is a **blocking validation gap**, reported as such.

cpppo has no backplane and OpENer routes directly ⇒ both sim configs omit `slot`; the
`slot`/backplane path stays a lab-PLC concern (§12.4).

### 11.6 The second independent poll target — libplctag `ab_server` (external container)

**libplctag's `ab_server`** (`libplctag/libplctag`, `src/tools/ab_server`, MPL-2.0) is the CIP PLC
simulator libplctag tests its own client against — a C implementation independent of both `enip` and
cpppo, so a genuine *second* poll conformance peer. `test-infra/ab-server/Dockerfile` compiles the
self-contained POSIX C sources (a single `-I src` for one header; ab_server's own `utils.c` supplies
the referenced symbol) and runs it as ControlLogix on the backplane path `1,0`, serving the §11.1
tag layout (ab_server requires an explicit array size on every CIP tag, so scalars are `[1]`).

**What it uniquely adds: the Unconnected_Send route path.** ab_server dispatches read/write only when
the request arrives wrapped in a real Unconnected_Send (`0x52`) to the Connection Manager (or over a
connected session); a bare Message-Router request hits its `default` → `0x08`. So the live suite runs
with `ClientOptions.route = RoutePath::backplane_slot(0)`, and `enip` wraps every read/write in a
`0x52` with the backplane-slot route — the CompactLogix/ControlLogix path cpppo (direct UCMM) never
exercises. **Confirmed live (S8):** connect (RegisterSession); scalar REAL / DINT / REAL[8]-array
reads with exact seeded values; write + read-back of `FILL_SETPOINT`; a nonexistent tag returns a
typed per-tag CIP error (`0x03`) while a real tag stays GOOD in the same session
(`crates/enip/tests/live_ab_server.rs::ab_server_live_read_write_routed`).

**Browse: NOT served.** Verified in `cip.c` (the `0x55` case is absent from `cip_dispatch_request`;
the `CIP_LIST_TAGS` bytes are commented out) and across the repo's full git history: ab_server has
*never* implemented Get Instance Attribute List. It answers `0x55` with `CIP_ERR_UNSUPPORTED`
(`0x08`), which `enip` surfaces as a typed refusal
(`ab_server_live_browse_is_gracefully_refused`) — so **ab_server does not close the browse gap**
(contrary to a common assumption that it is the libplctag "LIST_TAGS" server); EthernetIPSharp does
(§11.7).

**Two sim-side spec-conformance patches (S8), applied in the Dockerfile, NOT to `enip`.** ab_server's
*encapsulation* layer is stricter than the spec (Vol 2 §2-4) in two ways that reject any client which
stamps a Sender Context — `enip` does, as do most real clients, and cpppo/OpENer both accept it, so
these are ab_server limitations, not `enip` bugs (`enip`'s RegisterSession is proven against cpppo
*and* OpENer): (1) RegisterSession rejects a non-zero Sender Context, though the field is opaque and
merely echoed; (2) ab_server echoes an unassigned `plc->sender_context` (always `0`) instead of the
request's Sender Context, which `enip`'s reply-correlation (one in-flight request keyed on a
monotonic context, §10.3) requires. Two one-line `sed` patches in `test-infra/ab-server/Dockerfile`
make ab_server *more* spec-compliant (accept any context; echo the request's context); its CIP
read/write/error logic is untouched, so it stays a fully independent peer. **No `enip` change was
needed** for ab_server.

### 11.7 The independent browse target — EthernetIPSharp (external container)

**EthernetIPSharp** (`CristianMori/EthernetIpSharp`, C#, MIT) is a third, fully independent
EtherNet/IP implementation whose `LogixDispatcher`/`SymbolObject` serves Read/Write Named Tag AND —
uniquely among the container sims — the Logix tag-LIST service **Get Instance Attribute List
(`0x55`) on the Symbol class (`0x6B`)**. It is therefore the peer that **closes the `sb/browse`
gap**: the first genuine on-the-wire validation of `enip::list_tags` against a real, non-ours `0x55`
implementation (previously exercised only against `duplex` fixtures). `test-infra/ethernetip-sharp/
Dockerfile` builds the dependency-free library projects with the .NET 8 SDK and runs a small host
(`test-infra/ethernetip-sharp/Program.cs`, which overwrites the repo's loopback-only sample host to
bind `0.0.0.0` and serve the §11.1 tag layout).

**Confirmed live (S8)**, read/write cross-check: scalar REAL / DINT reads with exact host-seeded
values; REAL[8] array read; write + read-back of `FILL_SETPOINT`; a nonexistent tag returns a typed
per-tag CIP error (`0x05`) while a real tag stays GOOD
(`crates/enip/tests/live_ethernetipsharp.rs::sharp_live_read_write`). **Browse (`0x55`), the
gap-closer:** `enip::list_tags` pages a real Get-Instance-Attribute-List reply to completion and
decodes it correctly — the seven defined tags enumerate with their symbol-type words (REAL `0x00CA`,
DINT `0x00C4`, REAL[8] `0x20CA`), scalars value-supported and the array value-unsupported (array
dims), exactly as `SymbolType` decodes them (`sharp_live_tag_browse_enumerates`). S8's scope was the
single-page request/decode, and for that **no `enip` change was needed** — the `0x55` request
encoding and page decode were already correct. The *cursor* contract was changed later (D-ENIP-19,
below); S8 validated neither the cursor width nor the paging rules.

**Confirmed live (PR-4 / F7 browse cursors)**
(`sharp_live_browse_cursor_walk_and_32bit_instance_segment`):

* **Exactly-once enumeration.** The walk pages from the start of the instance space on the reply's
  own status: 7 tags over 1 page, instance ids `[2,3,4,5,6,7,8]`, strictly ascending, no name twice,
  terminating because the reply says so rather than because a caller-side page cap fired.
* **The 32-bit logical instance segment on the wire.** `list_tags(0x0001_0000)` and
  `list_tags(u32::MAX)` emit the `0x26` form (`26 00 00 00 01 00`) where a small cursor emits
  `24 xx`. EthernetIPSharp parses both and answers at the CIP layer — general status `0x16`, "no such
  instance" — not `PathSegmentError` (`0x04`) and not `InvalidPathSize` (`0x26`), and without
  dropping the session (a following full walk still returns the same seven tags). **This is the
  independent-implementation validation of the `0x26` encoding**, which no container sim can
  otherwise exercise because none serves more than 65 535 symbol instances; the golden vectors
  (PROTOCOL-DESIGN §12.4) pin the bytes, and this proves a foreign decoder reads them.

**Recorded peer limit — mid-set cursor resume is not bench-provable here.** EthernetIPSharp serves
the enumeration only from the class-level start instance (`0x24 0x00`): it returns its whole symbol
table in one page with no cursor, answers `ServiceNotSupported` (`0x08`) for a start instance that
exists, and `0x16` for one that does not. So *resuming a real `0x55` server mid-set* has no peer on
this bench, and joins the §14.6 lab-hardware row alongside the 32-bit multi-page walk. The live test
asserts the peer's actual answer in either branch — a correct resumed page, or a **typed** CIP
refusal — so it can never pass by silently observing nothing.

**The adapter-layer `sb/browse` path reaches this peer — for one page.** `EipSession::browse` starts
an uncursored browse at symbol instance **0** — the bottom of the instance space, and the only start
instance EthernetIPSharp's Symbol object serves. Measured through the real client: `list_tags(0)` ⇒ 7 records,
`list_tags(1)` ⇒ `Err(Cip(Unknown(0x16)))` with `is_transient() == false`, which the adapter would
map to `BROWSE_FAILED`. Starting at 1 would therefore have made `sb/browse` fail outright against the
bench's only real `0x55` server, and on any device would have skipped a symbol sitting at instance 0
— the same silent-skip class as a truncated page returning the device's own cursor (D-EIP-29). This
is why the paging spec's `None ⇒ 1` default was overridden on the evidence:
`eip::session::parse_browse_cursor(None) == 0`, guarded by
`an_uncursored_browse_starts_at_instance_zero` (§12.3), and the simulator inherits it through the
same parser.

**The obtainable adapter-layer leg is page 1, and it is captured.** `sb/browse` with no cursor and
`max: 2` against this peer answers `["LINE_SPEED", "FILL_TEMP"]` with `next = Some("4")`. That single
page proves both halves of the cursor contract on a real device page: the walk starts at instance 0
(the peer serves nothing else), and the truncation cursor resumes from the last record actually
**returned** — instance 3 ⇒ `"4"` — not from the device's own cursor over the full seven-record page.

**Page 2 is not obtainable against this peer, so the multi-page adapter-layer walk is not bench
evidence.** Sending `"4"` back is refused: EthernetIPSharp serves the enumeration only from the
class-level start instance and refuses every non-zero start — CIP `0x08` for a start instance that
exists (the cursor case), `0x16` for one that does not. The peer has no resume capability at all, so
an `sb/browse` walk over more than one page cannot be run here, at `max: 2` or any other page size.
The refusal is what the `start != 0` branch of `EipSession::browse` reports as `BROWSE_FAILED` naming
the refused instance rather than `BROWSE_UNSUPPORTED` (§10.1): the service demonstrably exists —
page 1 came from it. (The run that measured this predated that branch and saw the misleading
`BROWSE_UNSUPPORTED`; the mapping split is covered by
`browse_refused_on_a_resume_is_a_failed_page_not_an_unsupported_device`.) The multi-page
adapter-layer walk stays on the §14.6 real-Logix lab row alongside mid-set resume and the 32-bit
multi-page walk, and is claimed nowhere as proven. The enip-layer legs above already drive
`list_tags` from 0 directly.

All device sims are external containers (no in-crate CI fallback, user decision). ab_server and
EthernetIPSharp are bare TCP/CIP targets (no class-1 UDP), so unlike OpENer they run correctly under
Docker-Desktop-for-Windows port publishing. If a required target is unavailable for a release, that
is a **blocking validation gap**, reported as such.

### 12.2 Coverage denominator exclusions

**No product file is excluded.** Every driver, every loop, and every live-socket backend in this
repo is inside the denominator and unit-tested, because each one takes its live dependency through an
injected seam rather than reaching for it:

| Seam | Production | Under test |
|---|---|---|
| `publish::Publisher` | `publish_sink::FacadePublisher` over the `data()` facade | a recording publisher with a settable failure flag |
| `device::DeviceBackend` / `DeviceSession` / `PushSession` | `eip::live::EipBackend` over the `enip` stack | scripted sessions (queued read outcomes, write journal, close counter) |
| `app::EventSink` | `supervisor::FacadeEventSink` over the `evt` surface | a recording sink |
| `metrics::DeviceMetrics` / `Health` | a `MetricService`-backed instance | the same types over a recording metric service |
| `credentials::CredentialService` | the component's vault | a `LocalVault` + `FileKeyProvider` in a tempdir |

So `poll_driver.rs`, `push_driver.rs`, `reconnect.rs`, `security_lifecycle.rs`, `lifecycle.rs`, and
`reload.rs` all run as ordinary unit tests — on a paused clock wherever the behaviour is a cadence, a
deadline, or a backoff; on real time only where the leg does real loopback TLS I/O (the EST
enroll/renew legs). `eip/live.rs` runs against a scripted EtherNet/IP peer on a loopback
`TcpListener` (plaintext and TLS) plus a test-owned UDP socket standing in for the class-1 target —
no container, no device, no fixed port, Windows and Linux alike (§12.3).

Two disciplines make those paused-clock tests mean something. **Every deadline is measured on the
runtime clock** (`tokio::time::Instant`) rather than the system clock, so a wait that is serviced
part-way through — a control verb arriving inside a backoff window — resumes its remaining time
instead of silently re-arming; only sample capture instants stay on `std::time::Instant`, because
they are wall-clock evidence about a frame. And **where a backoff rung is the claim**, the test pins
the full-jitter fraction (`testutil::JitterGuard`) so the wait is exactly that rung's cap: an
unpinned `wait ≤ cap` assertion is one-sided, and would pass a ladder that stopped resetting its
attempt counter on most runs.

The exclusion list is therefore three **non-product** categories:

- `crates/enip/tests/live_{cpppo,opener,ab_server,ethernetipsharp,tls,cip_security}.rs` — the six
  live-peer conformance suites (§11.3). Each probes its peer's port and self-skips when the container
  is down, so where the peers are absent they are dead test code rather than evidence about product
  code. They exist to check this stack against **independent implementations** — cpppo, OpENer,
  libplctag `ab_server`, EthernetIPSharp, an OpenSSL TLS terminator, and OpENer's `CIPSecurity`
  branch — which is conformance evidence, a different question from coverage.
- `crates/enip/fuzz/` — libFuzzer harnesses. They *exercise* covered product code; they are not
  product code. (Also a separate workspace, so the coverage job does not even build them.)
- `src/testutil.rs` — `#[cfg(test)]`-only recording doubles, the throwaway PKI / in-process EST
  responder they share, and the backoff-jitter pin, compiled out of the shipped binary.

**What stays inside the denominator and reads uncovered**, counted against the gate rather than
laundered out of it:

- `src/supervisor.rs` (185 instrumented lines) — the EdgeCommons construction glue: `App`,
  `RuntimeLauncher`, `FacadeEventSink`, `DroppedEvents`. Every path needs an `Arc<EdgeCommons>`, and
  the core library's offline test constructor is `pub(crate)`, so a dependent crate cannot build a
  runtime in a unit test. It makes no runtime decision of its own — what to launch, stop, or keep is
  decided in `reload.rs`, how a teardown is bounded in `lifecycle.rs`, and what a running instance
  does in `reconnect.rs` / `security_lifecycle.rs` / the two drivers, all of them tested.
- `src/publish_sink.rs` (3 lines) — `FacadePublisher::publish_update`, the single `.await` on the
  `data()` facade. The `DataFacade` has the same offline-construction problem.
- `src/main.rs` (16 lines) — the binary entry.
- The bodies of the three **in-source** live tests — `eip/tls.rs`'s client-cert-rotation and
  near-expiry tests against the `:2221` stunnel terminator, and `eip/est/tests.rs`'s enrollment test
  against the `:8443` globalsign/est server — read uncovered on a bench with those containers down.
- The protocol crate's own live-socket runtime — `enip/io.rs`'s class-1 UDP
  `IoManager`/`manager_task`/`IoConnectionHandle`, `client/io_service.rs`, and `client/mod.rs`'s TCP
  connect — validated by the live OpENer/cpppo suites, and still counted here.

Those uncovered paths are exercised by the HOST / full-system E2E and the deployed regression
(§12.4). Do NOT add exclusions to dodge the gate; add tests.

### 12.2b Fuzzing (D-EIP-19)

The protocol crate's cargo-fuzz targets are specified in PROTOCOL-DESIGN §12.3 (one target per

- **Push-mode runtime note (all packs)**: a push instance binds an **ephemeral** UDP source port of
  its own and advertises that address to the device in the ForwardOpen's Sockaddr Info items; `2222`
  is the **target's** destination port for the O→T direction, never a listening port on the adapter.
  There is therefore no fixed inbound port to open. The reachability requirement is that the device
  can send UDP **to the address the adapter advertised** — the adapter's own IP on an unpredictable
  high port — which means no NAT and no port-based filtering of the return path between device and
  adapter. Concretely: compose puts the adapter and the target on the same network (§11.2);
  Greengrass host networking is already flat; on Kubernetes no `containerPort` is declarable or
  needed (`containerPort` is informational, and the port is not known until the connection opens) —
  a cluster-internal peer reaches the pod IP directly, while a **real PLC outside the cluster**
  requires the pod's advertised IP to be routable from the device network, i.e. `hostNetwork: true`
  or a routable pod CIDR. Poll-only deployments open no UDP port.

## 14. Limitations & deviations

Surfaced up front, per the fidelity contract. Each also appears (present-tense, no roadmap
language) in the user-facing docs where relevant.

1. **Push writes are not device-acknowledged.** Implicit I/O has no per-write CIP confirmation;
   a push `sb/write` `ok:true` means the value rides the next cyclic O→T frame (§7.3,
   `applied: "next-frame"`). Poll writes remain CIP-acked. (User-docs phrasing: state both
   behaviors as plain present fact.)
2. **No structures/UDTs, no strings; BOOL arrays are experimental.** Supported values are CIP
   elementary scalars and 1-D arrays thereof (§5.1), in both modes. Logix STRING is a UDT ⇒
   unsupported; config validation rejects them; browse marks them `supported: false` (D-EIP-16).
   A poll `bool` signal with `arrayCount` is **accepted with a per-signal validation WARN**: the
   adapter reads whichever representation the device declares — byte-per-element, or the Logix
   `DWORD` packing (1756-PM020) unpacked LSB-first (D-EIP-35) — but the packed path is unvalidated
   against physical hardware, its bit order and packed element-count denomination await a real
   controller, and a write to a tag observed packed is refused. The adapter has no device-family
   detection, so the experimental label covers the feature as a whole. Scalar `bool` and push assembly `bool` array fields are unaffected. Array
   lengths are bounded to `1..=65535` and a reply that does not carry the configured number of
   elements is a BAD sample, never a shorter array published GOOD (D-EIP-33).
3. **No CIP Multiple Service Packet batching** — one request per signal per cycle in poll mode
   (D-EIP-15); `requestsPerCycle` makes the cost observable. Large signal counts want fewer,
   larger poll groups at longer intervals — or push mode, which has no per-signal request cost.
4. **`sb/browse` is device-dependent.** The tag-list service is a Logix-family capability;
   generic CIP devices (incl. plain I/O adapters like OpENer) answer `BROWSE_UNSUPPORTED`.
   Program-scoped enumeration covers program-prefixed symbol paths (PROTOCOL-DESIGN §7.3);
   deeper nested-structure iteration is not promised in v1. Push discovers nothing by itself —
   the assembly layout is configuration, there is no wire-discoverable field map.
5. **CIP Security — Phases 1, 2a, 2b and 2c shipped on the explicit path; DTLS/commissioning are
   the roadmap.** Poll (explicit-messaging) instances run over TLS (EtherNet/IP over TLS, TCP 2221,
   mutual X.509) via `connection.security` — `enip::connect_tls` behind the crate `tls` feature,
   `ClientConfig` built by the adapter from vault/file material (**D-EIP-21**; §4.2, §7.1, §8.2;
   DESIGN-cip-security.md §3). Only AEAD suites are negotiated (`rustls`, `tls12` on: the three
   TLS 1.3 suites plus six TLS 1.2 ECDHE suites — four AES-GCM, two ChaCha20-Poly1305; `cipherSuites`
   only narrows that set), so CBC, NULL and PSK are unreachable; CBC-only legacy
   firmware is the documented interop boundary (typed `NoCipherOverlap`). A `mode: push` instance
   configured with TLS is refused at validation — class-1 implicit I/O stays plaintext UDP 2222
   (**no silent downgrade**; CT23-deprecated TLS-session-opens-plaintext-I/O is not done).
   **Phase 2a (security-posture reads) shipped:** on connect the adapter reads the target's CIP
   Security (0x5D), EtherNet/IP Security (0x5E), and Certificate Management (0x5F) objects and surfaces
   the decoded posture on `sb/status.security.target` + `targetSupportsCipSecurity` (**D-EIP-22**;
   §4.1, §7.1; DESIGN-cip-security.md §4.1). The `enip` crate carries typed, bounds-checked
   (`WireReader`) decoders for these objects over the shipped `get_attribute_single` service (no new
   transport, no feature gate). A device that implements none of them reports
   `targetSupportsCipSecurity: false`, never an error (the generic-CIP-device path, validated against
   cpppo and the OpENer `CIPSecurity` branch). **Phase 2b (vault-native managed trust store + client-cert
   lifecycle/rotation) shipped (D-EIP-23):** the `ca.trustStore`/`ca.list` styles build a managed trust
   store (CA-rollover grace via the vault's version window), and a per-instance cert-lifecycle task
   picks up a rotated client cert / trust store from the vault and reconnects so it takes effect without
   a restart, monitors client-cert expiry (`certExpiryDays` gauge; `cert-expiring`/`cert-expired`
   events; refuse-connect on an expired cert), and reflects it all on `sb/status.security`
   (`trustStore`, `clientCertSerial`, `clientCertExpiryDays`, `certReloads`). Validated end-to-end over
   the stunnel/cpppo TLS peer (rotate the vault → next connect presents the new serial; a near-expiry
   cert fires the event). **Phase 2c (EST enrollment) shipped (D-EIP-24):** the adapter enrolls and
   renews its own client certificate from a plant EST server (RFC 7030, `src/eip/est.rs`) and writes
   it to the vault, where the Phase-2b watcher reloads it and reconnects — validated against the
   independent globalsign/est server (`test-infra/est/`) plus an OpenSSL golden PKCS#7 vector;
   enrollment against a real device-PKI remains on the §14.6 lab row. **Roadmap: DTLS on the
   implicit path** (see DESIGN-cip-security.md §4/§6 for the phase gates).
6. **Lab-hardware-only validation paths, declared:** the `slot`/backplane routing path,
   connected class-3 messaging — including **idle-window keepalive semantics against real Logix**
   (whether a genuine ControlLogix Connection Manager enforces the inactivity watchdog the ¾-window
   keepalive keeps the session off, PROTOCOL-DESIGN §7.6 / D-ENIP-18; the bench proves the probes
   are well-formed, flow on cadence, and survive a multi-window idle against OpENer/cpppo) —
   **browse pagination on a controller-sized tag set** (multi-page `0x55` walks — at the `enip` layer
   and at the adapter's `sb/browse` layer alike — mid-set cursor resume, and 32-bit instance cursors
   beyond 65 535 symbols — PROTOCOL-DESIGN §7.3 / D-ENIP-19; the bench proves the exactly-once walk,
   that an independent implementation parses the `0x26` segment, and one real `sb/browse` page with a
   truthful truncation cursor, but EthernetIPSharp serves its whole symbol table in one page and
   refuses every non-zero start instance, so nothing past page 1 has a container peer at either
   layer, §11.7) —
   **Logix BOOL-array (DWORD) packing** — a `BOOL[n]` tag is served as a `0x00D3` DWORD array
   (1756-PM020), and the adapter translates it LSB-first into the configured booleans (D-EIP-35);
   what a real controller still has to confirm is the **bit order**, the **element-count
   denomination** of a packed Read Tag (BOOLs or DWORDs — the adaptive first read converges either
   way, at the cost of one BAD sample), and the **masked read-modify-write** a packed write needs
   and which is refused until then. cpppo is a Logix emulator with a fidelity gap at exactly this
   point (it serves BOOL arrays byte-per-element), so the packed path cannot be validated here at
   all: a green bench exercises only the byte-per-element control path, and the packed evidence is
   unit + duplex fixtures constructing DWORD replies. Until a controller answers, BOOL arrays ship
   **labelled experimental**, warned per signal at validation (D-EIP-16) —
   **multicast T→O consume**, push against a real PLC/remote-I/O
   device, and **CIP Security against a certified Vol 8 device** (port policy with 44818 closed,
   Vol-8-exact suite lists, `Send Certificate Chain`/`Verify Client Certificate` corner semantics) —
   cpppo has no chassis/class-1, OpENer exercises P2P direct connections, and the CIP Security Phase-1
   layer is validated against an OpenSSL/stunnel-over-cpppo terminator (an independent TLS + EtherNet/IP
   pair at exactly the changed layer), not a real CIP-Security PLC (DESIGN-cip-security.md §5.2). Until
   real hardware passes §12.4's lab row, treat these config paths as
   implemented-but-hardware-unvalidated. Declared validation gaps, not silent ones. The
   extended-port (> 14) route encoding is additionally **disabled** pending a captured
   conformance vector (PROTOCOL-DESIGN D-ENIP-13).
7. **`sb/pause`/`sb/resume` are promoted into the southbound contract** (D-EIP-3, resolved):
   `SOUTHBOUND.md` §2.2 now lists `sb/pause`/`sb/resume`/`reconnect`/`repoll` as the standard
   instance-control family, with the `PAUSED` refusal code this adapter implements.
8. **Deviations vs the references, with rationale:** no subscription/monitored-item model
   (push/class-1 is the protocol's native cyclic model and is supported instead; OPC UA's
   filtered-subscription semantics do not transfer); no regex include/exclude signal matching
   (declaration-based like Modbus, D-EIP-7); allow-list `writes.allow[]` instead of Modbus's
   legacy `write.enabled` boolean (strictly stronger, D-EIP-5); `sb/subscribe-preview` from
   §2.2 is N/A (no dynamic subscription spec to preview — push connections are config-declared)
   and is deliberately not registered.
9. **Pause state does not survive restart** (in-memory; D-EIP-14/D-EIP-20) — nor an instance
   restart performed by a configuration reload (D-EIP-28, §10.4): pause survives only on instances
   the reload leaves untouched. `sourceTs` is never emitted (D-EIP-11).
10. **One mode per instance** (D-EIP-2): a device needing both poll and push telemetry is two
    instances (they share nothing but the target device; each has its own session/connection).

### Open questions (for the user — none block S1–P2)

1. Should `sb/pause`/`sb/resume` accept an optional `"groups": ["fast"]` selector (pause one
   poll group)? v1 designs instance-granularity only; group-granularity is a cheap additive
   later if wanted.
2. Metric family prefix `EtherNetIp*` mirrors `Modbus*`/`OpcUa*`. Confirm the spelling
   (alternative `Enip*`) before S5 — this doc pins `EtherNetIp*` (and `EtherNetIpIo` for the
   push family).
3. When pause/resume is later promoted into core `SOUTHBOUND.md`, should this adapter's
   `write-audit` event type also be proposed as a cross-adapter convention (Modbus has an
   equivalent, OPC UA does not)? Not needed for this build.
4. Should the protocol crate eventually publish (crates.io or the org registry) as a standalone
   EtherNet/IP stack? This design keeps `publish = false` and the package name `ec-enip`
   (PROTOCOL-DESIGN §3.1); publication would want a naming/ownership decision first.
5. OpENer's sample-app assembly instance ids/sizes are pinned at S1-push time (§11.5). If the
   sample layout is awkward for the E2E narrative, do we patch OpENer's demo app in our
   Dockerfile (kept: a ~20-line config change) or adapt §4.6's worked config to whatever it
   ships? Default: adapt the config; do not fork the target.
